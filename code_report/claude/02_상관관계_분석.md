# 02. 상관관계 분석 — "DB 가 쌓일수록 평가엔진이 좋아지는 구조인가?"

> 이 문서가 이번 분석의 **본론**입니다. 결론부터 말하고, 코드 근거로 증명한 뒤,
> 선순환 고리가 끊어진 지점 4곳 + 숨은 리스크 1곳을 짚습니다. 코드는 변경하지 않았습니다.

---

## 1. 결론 요약 (3줄)

1. **코멘트 품질은 YES** — IssueTable 사람 코멘트 → eval DB `label` → 선례검색 → AI Comment 인용,
   이 선순환의 뼈대는 **이미 연결되어 있고 설계 방향이 맞다.** 코멘트가 쌓일수록 AI Comment 의
   "과거 사례 인용"은 실제로 풍부해진다.
2. **판정 정확도는 NO(현재는)** — status/severity 판정(L0~L4)은 100% 룰 기반이라
   **DB 가 아무리 쌓여도 판정은 변하지 않는다.** 데이터로 판정이 좋아지는 유일한 경로(calibrate)는
   수동 오프라인 도구인데, **그 재료(features)가 현재 운영 흐름에서는 전혀 쌓이지 않는다.**
3. **따라서 "쌓일수록 좋아지는 구조"는 절반만 완성** — 끊어진 고리 4곳(§4)을 이으면 완성된다.
   대부분은 eval_analyzer 를 **수정하지 않고** report_server 쪽 추가만으로 이을 수 있다(→ 04 문서).

---

## 2. 질문을 정확히 쪼개기

"엔진 퀄리티(정확도)"는 이 시스템에서 **서로 다른 두 가지**로 나뉜다. 둘을 섞으면 판단을 그르친다.

| 구분 | 무엇 | 결정하는 것 | DB 축적의 영향 |
|---|---|---|---|
| **① 판정 정확도** | status(CRITICAL~OK)·primary_signature 가 엔지니어 판단과 일치하는가 | L0~L4: 그 회차 통계 + `rules/*.yaml` 임계값 | **없음** (런타임 기준) / calibrate 로만 간접 반영 (수동) |
| **② 코멘트 유용성** | "분석방향 코멘트"가 실제로 도움이 되는가 | L5: 룰 골격 문장 + **과거 선례 human_comment 인용** | **있음** — 선례가 많고 좋을수록 향상 |

## 3. 코드로 증명 — 어디가 DB 를 읽고, 어디가 안 읽나

### 3.1 판정(L0~L4)은 DB 를 읽지 않는다

| 단계 | 함수 | 입력 | DB 조회 |
|---|---|---|---|
| L3 signature 판독 | [signatures.py:51](../../eval_analyzer/eval_engine/pipeline/signatures.py#L51) `evaluate` | case_ctx / features / raw_metrics | **없음** — 임계값은 YAML 로더([_rules.py:19](../../eval_analyzer/eval_engine/pipeline/_rules.py#L19))에서만 |
| L4 status 결정 | [status.py:27](../../eval_analyzer/eval_engine/pipeline/status.py#L27) `decide` | case_ctx / features / sig_result | **없음** |

과거 label 의 다수결, 유사 case 의 status 참조, 빈도 통계 — 이런 로직은 코드 어디에도 없다.
`root_cause_category`(사람의 원인 분류)도 판정으로 역류하지 않는다.
**같은 데이터를 넣으면 DB 가 0건이든 100만 건이든 판정은 동일하다** (engine_version 이 같은 한).

### 3.2 DB 를 읽는 유일한 런타임 지점 = L5 선례검색

호출 사슬: [api.py:50](../../eval_analyzer/eval_engine/api.py#L50) → [recommend.py:14](../../eval_analyzer/eval_engine/pipeline/recommend.py#L14) `find_precedents` → [precedent_client.py:14](../../eval_analyzer/eval_engine/precedent_client.py#L14) `search` → [store.py:470](../../eval_analyzer/eval_engine/store.py#L470) `search_precedents`.

- 매칭: 같은 value_type (+family_product) → item 이름 **difflib 문자열 유사도 ≥ 0.70**
- 활용: human_comment 가 있는 선례를 우선 정렬해 → 템플릿 코멘트에
  `"(과거 사례 N건: … / … / …)"` 로 **전부 이어붙임** ([recommend.py:24-26](../../eval_analyzer/eval_engine/pipeline/recommend.py#L24-L26))
- 저장: 어떤 선례를 인용했는지 `eval_precedent` 테이블에 이력 기록

→ **DB 축적의 효과 = 이 인용문이 풍부해지는 것.** 그 이상도 이하도 아니다.

### 3.3 데이터로 임계값이 진화하는 유일한 경로 = 오프라인 calibrate

[calibrate.py:96](../../eval_analyzer/eval_engine/calibrate.py#L96) `recalibrate` — 쌓인 `features` 를 item_class 별로 모아
분위수(퍼센타일)를 계산 → `thresholds.yaml` 의 item_class 섹션을 재작성 → 새 engine_version 등록.

- item_class 당 표본 **최소 30건**(min_n) 필요
- **사람이 CLI 로 직접 실행**해야 한다 — 자동으로 돌지 않는다
- cpk_warn 같은 업계 표준값은 보정 대상이 아님 (통계적 산포 지표들만)

**비유**: 이 엔진은 "고정 기준의 건강검진 판독기"다. 검진 결과가 쌓인다고 판독 기준이 저절로
바뀌지 않는다. 다만 ① 소견서에 "비슷한 환자들의 과거 처방"을 인용해 주고(L5),
② 의사가 마음먹고 통계를 돌려 기준표를 개정(calibrate)할 수는 있다.

## 4. 선순환 고리가 끊어진 지점 — 정밀 진단

목표하는 선순환과 현재 상태를 겹쳐 그리면:

```
                 [목표 선순환 루프]
   ┌──────────────────────────────────────────────┐
   │                                              ▼
 web_report 데이터·코멘트 ──▶ eval DB 축적 ──▶ 엔진 참조/보정 ──▶ 더 정확한 판정·코멘트
   ▲                                              │
   └────────────── 사용자 피드백 ◀────────────────┘

                 [현재 실제 연결 상태]
 코멘트(human_comment) ──✅──▶ label ──✅──▶ L5 선례 인용   (연결됨 — 코멘트만 좋아짐)
 판정 재료(features)   ──❌──▶ (안 쌓임)      ──▶ calibrate  (끊어짐 ①)
 사람 판정/원인 분류    ──❌──▶ (입력 UI 없음) ──▶ 룰 검증    (끊어짐 ②)
 AI Comment 채택 여부  ──❌──▶ (기록 안 함)   ──▶ 정확도 측정 (끊어짐 ③)
 과거 문서 대량 적재    ──❌──▶ (파서 스텁)    ──▶ 초기 DB    (끊어짐 ④)
```

### 끊어짐 ① — calibrate 의 재료(features)가 운영 흐름에서 전혀 안 쌓인다

- AI Comment 경로는 `evaluate(persist=False)` — **미리보기 모드라 features 무기록**
  ([ai_comment.py:153](../../web_report/ai_comment.py#L153)). 이건 eval_analyzer 소유 DB 를 보호하는 올바른 규약이지만,
  부작용으로 판정 지표가 어디에도 축적되지 않는다.
- eval_export 경로는 `raw_metrics`(cpk 등 요약통계) + `label` 만 기록하고
  **`features` 와 `evaluation` 은 기록하지 않는다** ([eval_export.py:273-315](../../web_report/eval_export.py#L273-L315)).
- calibrate 는 `features` 테이블이 재료다 ([calibrate.py:29](../../eval_analyzer/eval_engine/calibrate.py#L29) `_collect_by_item_class`).

**결과**: 지금 구조로는 web_report 를 아무리 오래 운영해도 calibrate 를 돌릴 표본(item_class 당 30건)이
영원히 0건이다. **"쌓일수록 판정이 좋아진다"의 유일한 공식 경로가 입구부터 막혀 있다.**

### 끊어짐 ② — label 이 반쪽짜리다 (human_comment 만 있고 정답 등급이 없다)

eval_export 가 넣는 label 은:

| label 컬럼 | 값 | 의미 |
|---|---|---|
| `human_comment` | ✅ "[PTE] …\n[개발] …" 병합 텍스트 | 선례 인용에는 충분 |
| `human_status` | ❌ None | 사람이 본 진짜 등급 (엔진 status 의 **정답지**) |
| `root_cause_category` | ❌ None | equipment/process/design/spec/unknown |
| `engine_comment_accepted` / `comment_modified` | ❌ None | AI 코멘트 채택 여부 |
| (연계) `case_outcome.action/result` | ❌ 미기록 | 실제 조치와 그 결과 |

스키마([store.py:99-110](../../eval_analyzer/eval_engine/store.py#L99-L110))와 저장 함수
`insert_label`([store.py:418](../../eval_analyzer/eval_engine/store.py#L418))은 이 값들을 **전부 받을 준비가 되어 있다.**
못 채우는 이유는 단 하나 — **IssueTable 에 입력 UI 가 없어서**다. 코멘트 자유 텍스트만 받는다.

**왜 중요한가**: "엔진 판정 vs 사람 판정"을 비교할 정답지가 없으면 —
- 엔진 정확도를 **측정조차 할 수 없고** (지금 몇 % 맞는지 아무도 모른다)
- calibrate 후속 기능으로 예고된 "룰 precision/recall 검증"([eval_analyzer/CLAUDE.md](../../eval_analyzer/CLAUDE.md) 미구현 목록)도 재료가 없다.

### 끊어짐 ③ — AI Comment 에 대한 피드백이 버려진다

사용자가 AI Comment 를 보고 "맞네" 하고 그대로 두는지, 지우고 다시 쓰는지 —
이 신호가 엔진 정확도의 가장 값싼 측정 지표인데 현재는 아무 데도 기록되지 않는다.
스키마에는 이미 `engine_comment_accepted`, `comment_modified` 컬럼이 존재한다(위 표).
AI Comment 컬럼은 읽기 전용으로만 표시되고 ([tabs/issue_table.py:28-31](../../web_report/tabs/issue_table.py#L28-L31)),
사람 코멘트와의 관계는 추적되지 않는다.

### 끊어짐 ④ — 초기 DB 를 채울 대량 적재 수단이 미완성

선례검색이 힘을 쓰려면 **시작부터 선례가 어느 정도 있어야** 하는데(콜드스타트 문제),
과거 평가 문서를 자동으로 파싱해 넣는 도구(`ai_extract.extract_rows_from_text`)는
`NotImplementedError` 스텁이다 ([ai_extract.py:137-142](../../eval_analyzer/db_input/ai_extract.py#L137-L142)).
현재는 사람이 CSV 를 손으로 만들어야 한다. → 상세 진단과 설계는 [05_db_input_발전방향.md](05_db_input_발전방향.md)

### 리스크 ⑤ (숨은 것) — 쌓일수록 오히려 나빠질 수 있는 지점 1곳

선례검색 호출부는 **limit 없이** 전체를 반환받고 ([precedent_client.py:21-26](../../eval_analyzer/eval_engine/precedent_client.py#L21-L26),
[store.py:478](../../eval_analyzer/eval_engine/store.py#L478) "limit=None 이면 전체 반환"),
템플릿 코멘트는 **모든 human_comment 를 이어붙인다** ([recommend.py:24-26](../../eval_analyzer/eval_engine/pipeline/recommend.py#L24-L26)).

- 선례 10건: `"(과거 사례 10건: … / … / …)"` — 유용
- 선례 300건: 코멘트 한 칸이 수천 자 — **IssueTable 셀이 사실상 읽을 수 없게 된다**

즉 DB 를 열심히 쌓는 데 성공할수록 이 지점이 먼저 터진다. RAG 백엔드에는 top-k(기본 5) 상한이
설계되어 있지만 ([config.py:35](../../eval_analyzer/eval_engine/config.py#L35)), 기본 SQL 백엔드에는 상한이 없다.
→ 외부 담당자 요청 목록(03 문서 R-6)에 포함.

## 6. 종합 평가표

| 평가 항목 | 판정 | 한 줄 근거 |
|---|---|---|
| web_report ↔ eval_analyzer 연동 구조(경계·소유권·안정성) | **◎ 우수** | 단방향·2접점·conn 주입·멱등·실패 가시화 |
| 코멘트가 쌓일수록 AI Comment 가 좋아지는가 | **○ 그렇다** | label.human_comment → 선례 인용 루프 작동 |
| 판정(status)이 쌓일수록 좋아지는가 | **✕ 아니다** | L0~L4 는 DB 무관 고정 룰. calibrate 재료도 안 쌓임 |
| 엔진 정확도를 측정할 수 있는가 | **✕ 불가** | 사람 정답(human_status)·채택 신호 미수집 |
| 초기 DB 대량 적재 준비 | **△ 반쪽** | 정형 CSV 는 가능·완전체 label 가능 / 자동 파싱 스텁 |
| 대량 축적 시 안정성 | **△ 주의** | 선례 인용 무제한 이어붙임(§4 리스크 ⑤) |
