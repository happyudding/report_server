1. 결론 먼저 — 절반은 이미 맞고, 절반은 물길이 끊겨 있다

"정확도"를 두 가지로 나눠야 정확한 답이 나옵니다. 엔진의 출력은 ①등급 판정(status)과 ②분석방향 코멘트, 둘이기 때문입니다.

○ 코멘트는 YES

쌓일수록 좋아지는 구조가 이미 연결됨

IssueTable 사람 코멘트 → eval DB(label) → 선례검색 → AI Comment 에 "(과거 사례 N건: …)" 인용. 이 선순환의 뼈대는 지금도 작동하는 올바른 설계다.

✕ 판정은 NO (현재)

DB 가 아무리 쌓여도 판정은 변하지 않음

등급 판정은 100% 룰(YAML 임계값) 기반 — 과거 DB 를 전혀 읽지 않는다. 데이터로 기준을 개선하는 유일한 통로(calibrate)는 재료(features)가 지금 흐름에선 전혀 쌓이지 않는다.

△ 그래서

끊어진 물길 4개 + 리스크 1개만 이으면 완성

대부분 eval_analyzer 를 고치지 않고 report_server 쪽 추가만으로 가능. 유일한 엔진 수정 요청은 사실상 한 줄(선례 인용 상한)이다.

비유로 한 줄: 이 엔진은 "기준표가 고정된 건강검진 판독기"입니다. 검진 기록(DB)이 쌓인다고 판독 기준이 저절로 바뀌진 않지만, 소견서에 비슷한 환자들의 과거 처방(선례)을 인용해 주는 기능은 이미 있고, 기록이 충분히 모이면 기준표를 통계로 개정(calibrate)할 수도 있게 설계되어 있습니다. 문제는 그 "기록"이 지금 절반만 쌓이고 있다는 점입니다.

2. 전체 그림 — 누가 누구와 어떻게 연결되어 있나

파란색 = 우리(report_server) 소유·자유 수정. 노란색 = 외부 담당자 소유·동결(수정 불가). 엔진 코드를 가져다 쓰는(import) 곳은 규약상 딱 2곳입니다.

그림 1. 전체 관계도 — 의존은 report_server → eval_analyzer 한 방향뿐이고, 엔진 import 는 접점 ①②의 2곳뿐. 서버는 엔진 소유 DB 를 절대 건드리지 않고 자기 소유의 선례 DB(초록)에만 기록한다.
왜 이 구조가 좋은가: 외부 담당자 코드(노란 영역)와 충돌 없이 우리가 확장할 수 있는 경계가 명확합니다. 엔진의 저장 함수를 "연결(conn) 주입" 기법으로 재사용해 스키마가 항상 호환되고, 내보내기는 비동기(사용자를 기다리게 하지 않음)·멱등(재실행해도 중복 없음)이며, 실패하면 감사 로그와 관리자 화면 배지로 보입니다. — "학습하는 시스템"의 그릇으로서는 이미 잘 만들어져 있습니다.

3. 엔진 동작 원리 — 어디가 DB 를 읽고, 어디가 안 읽나

evaluate() 한 번 = 아래 7단계. 건강검진에 비유하면 접수→측정→정밀지표→소견 판독→등급→처방→결과지입니다.

그림 2. L0~L6 파이프라인 — 과거 DB 를 읽는 곳은 L5(초록) 하나뿐이고, 그 결과는 코멘트 문장에만 쓰인다.
추가로 알아둘 것 2가지: ① 코멘트를 자연어로 다듬는 LLM 기능은 스위치(설정)만 있고 본체가 미구현(스텁)이라 지금은 항상 "룰 문장 + 선례 나열" 템플릿입니다. ② 임계값을 데이터 분위수로 재보정하는 calibrate 도구가 있지만, 사람이 직접 실행해야 하는 오프라인 도구이고 재료(features 테이블, 유형별 30건 이상)가 필요합니다 — 이 재료가 지금 안 쌓이는 게 §4의 핵심입니다.

4. 선순환 진단 — 연결된 물길 1개, 끊어진 물길 4개

"쌓일수록 좋아지는 구조"가 되려면 아래 5개의 물길이 모두 흘러야 합니다. 현재는 맨 위 하나만 흐릅니다.

사람 코멘트 (IssueTable)→ eval DB label→ L5 선례 인용→ AI Comment 풍부화 ✅ 연결됨 — 지금도 작동
판정 재료 (features)⇢ 안 쌓임 (미리보기 모드 + export 미기록)⇢ calibrate 임계값 개선 ❌ 끊어짐 ①
사람의 정답 (등급·원인·조치)⇢ 입력 UI 없음 → 전부 빈칸⇢ 룰 정확도 성적표 ❌ 끊어짐 ②
AI Comment 채택/수정 여부⇢ 기록 안 함 (컬럼은 이미 존재)⇢ 정확도 측정 (채택률) ❌ 끊어짐 ③
과거 평가 문서 (대량)⇢ 자동 파싱 미구현 (스텁)⇢ 초기 선례 DB (콜드스타트) ❌ 끊어짐 ④

① calibrate 의 연료가 0건

AI Comment 평가는 미리보기 모드(persist=False)라 판정지표(features)를 저장하지 않고, 코멘트 내보내기도 요약통계와 label 만 기록한다. calibrate 는 features 가 유형별 30건 이상 필요하므로 지금 구조로는 아무리 운영해도 영원히 실행 불가.

② label 이 반쪽짜리

내보내는 label 에는 코멘트 텍스트만 있고 사람이 본 등급(human_status)·원인 분류(root_cause)· 조치/결과(outcome)는 전부 빈칸. DB 스키마와 저장 함수는 이 값들을 받을 준비가 이미 되어 있다 — IssueTable 에 입력 칸이 없을 뿐.

③ 피드백이 버려진다

사용자가 AI Comment 를 채택했는지, 지우고 다시 썼는지는 엔진 정확도의 가장 값싼 측정 지표인데 어디에도 기록되지 않는다. 기록용 컬럼(engine_comment_accepted 등)은 스키마에 이미 존재.

④ 초기 적재 깔때기가 미완성

"기존 평가 문서 복붙 → 자동 파싱" 훅이 미구현 스텁. 현재는 정형 CSV 를 사람이 손으로 만들어야만 넣을 수 있다. 단, 검증→변환→적재 뒷단은 전부 완성되어 있어 앞단만 만들면 된다.

⑤ 숨은 리스크 — "쌓을수록 오히려 나빠지는" 지점 하나

선례검색은 개수 제한 없이 전부 반환하고, 코멘트는 반환된 사람 코멘트를 전부 이어붙인다. 선례 10건이면 유용하지만 300건이면 셀 하나가 수천 자 — DB 적재에 성공할수록 이 지점이 먼저 터진다. 해법은 인용 상한(top-k) 한 줄 — 외부 담당자 요청 목록 1순위(R-1). 대량 적재를 시작하기 전에 요청해 둘 것.

6. 현재 vs 목표 — 무엇이 달라져야 하나

지금 (절반의 선순환)

코멘트→label →선례 인용
  • AI Comment 는 룰 문장 + 선례 나열 (LLM 미가동)
  • 판정 기준은 초기 YAML 그대로 고정
  • 정확도가 몇 % 인지 측정 불가 (정답지 없음)
  • 선례 DB 는 사실상 빈 상태에서 시작 (콜드스타트)

목표 (완성된 선순환)

코멘트+등급+조치→완전한 label →선례+성적표+calibrate →판정·코멘트 개선→채택률 상승 확인
  • 과거 문서 대량 적재로 첫날부터 선례 인용 동작
  • features 축적 → calibrate 로 임계값이 데이터를 따라감
  • human_status 정답지 → 룰 성적표로 정확도를 숫자로 관리
  • LLM 합성 + 인용 상한으로 코멘트가 읽기 좋은 한 문장

7. 해법 지도 — 누가 무엇을 고치나

파란 카드 = 우리가 eval_analyzer 무수정으로 할 수 있는 것(E). 노란 카드 = 외부 담당자에게 요청할 것(R). 굵은 테두리 = 우선순위 최상.

E-1 · 우리

IssueTable 라벨 입력 UI

코멘트 옆에 선택식 드롭다운(등급/원인/조치·결과) 추가 → 내보내기에 함께 실어 label 을 완전체로. 모든 "엔진이 좋아지는 미래"의 출발점. 엔진 저장 함수는 이미 이 값들을 받는다.

E-3 · 우리(+규약 합의)

features 축적 시작

환경변수(EVAL_DB_PATH)를 서버 소유 DB 로 지정하면 persist=True 평가가 엔진 수정 없이 features 를 우리 DB 에 쌓는다. 백그라운드 내보내기에서 세션당 1회 실행. "persist=False" 규약 문서 개정을 외부 담당자와 합의 후 진행.

E-2 · 우리

AI Comment 채택/수정 기록

👍/👎 또는 "채택" 버튼 → 채택률이라는 단일 숫자로 엔진 개선을 추적. 기록용 DB 컬럼은 이미 존재. 난이도 낮음.

E-4/v0 · 우리

db_input 외부 파서 (§8)

엑셀 복붙 → 자동 매핑 → 검증 → 적재. LLM 없이 v0 부터 시작 가능 — 콜드스타트 해소의 최단 경로.

E-5 · 우리

admin 검수 대시보드

기존 Eval DB 탭 확장 — label 커버리지 현황, 저질 코멘트 검수/삭제. 쌓이는 데이터의 질 관리 창구.

E-6 · 우리(계약됨)

RAG 선례검색 (장기)

핸드오프 문서가 이미 "report_server 담당자가 스텁 함수 1개만 구현"으로 계약해 둔 항목. 선례 수백 건 이후에 의미 — 서두를 필요 없음.

R-1 · 외부 요청 (1순위)

선례 인용 상한 (top-k)

사실상 한 줄 수정. 대량 적재 전에 반영되어야 §4-⑤ 코멘트 폭발을 막는다.

R-2 · 외부 요청

LLM 코멘트 합성 구현

스위치·설정은 준비 완료, HTTP 호출 본체만 미구현(예고된 후속). 선례가 쌓일수록 효과가 커지는 품질 도약 스위치.

R-3/R-4/R-5 · 외부 요청

추출기 계약 · 룰 성적표 · 보정 절차

R-3: "추출기는 우리가 밖에서 구현" 계약 확정(코드 0줄). R-4: 엔진 vs 사람 판정 비교 성적표(label 이 쌓인 뒤). R-5: calibrate 운영 절차 1쪽.

8. db_input 발전 방향 — "복붙 → 자동 파싱 → 적재" 5단계

좋은 소식: 파이프라인의 뒷단(검증→변환→적재)은 이미 완성·멱등입니다. 새로 만들 것은 앞단 두 조각뿐이고, 전부 eval_analyzer 밖에 둘 수 있습니다.

순서 전략: v0(LLM 불필요) — 기존 평가 문서가 대부분 표 형태라면 헤더 매핑만으로 목표의 80% 달성, 외부 담당자 일정과 무관하게 지금 시작 가능 → v1 — 보고서·메일 등 자유서식을 사내 LLM 으로 (환각은 ③검증이 걸러냄) → v2 — admin 패널 "선례 적재" 탭으로 통합.
무엇부터 넣나: ①사람 코멘트+원인+조치가 있는 과거 사례(선례 인용의 원료) → ②같은 item 의 표기 변형(유사도 0.70 매칭을 위해) → ③규격·통계가 있는 행 순. 코멘트 없는 fail 목록 단순 나열은 가치가 낮습니다.
안전수칙 2개: 적재 스크립트는 실행 중 엔진 설정을 덮어쓰는 단발 실행 전제이므로 서버 안에서 직접 부르지 말고 별도 프로세스로 실행할 것. 그리고 대량 적재 전에 R-1(인용 상한)부터.

9. 실행 로드맵 — 3단계

원칙: 데이터는 소급이 안 되므로 쌓기 시작(E-1/E-3)이 최우선, 쌓기 전에 넘칠 곳(R-1)부터 막고, 고급 기능(LLM·RAG)은 데이터가 모인 뒤에.

Phase 1 (0~1개월) — 쌓기 시작 + 안전장치

  • R-1 선례 인용 상한 요청 전달 — 외부 (한 줄)
  • v0 복붙 적재 도구 (LLM 불필요) — 우리
