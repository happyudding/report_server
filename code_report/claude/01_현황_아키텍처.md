## 0. 먼저 읽는 용어 사전 (초심자용)

| 용어 | 쉬운 설명 |
|---|---|
| **SQLite / .db 파일** | 서버 없이 **파일 하나**가 곧 데이터베이스인 경량 DB. `eval.db`, `report.db` 가 전부 SQLite 파일이다. 엑셀 파일 하나에 시트(테이블) 여러 개가 든 것과 비슷하다고 생각하면 된다. |
| **테이블 / 스키마** | 테이블 = DB 안의 표. 스키마 = "어떤 표들이 어떤 컬럼으로 존재하는가" 하는 설계도. |
| **import** | Python 에서 다른 폴더의 코드를 가져다 쓰는 것. "A 가 B 를 import 한다" = A 가 B 의 기능을 빌려 쓴다(의존한다). |
| **엔트리포인트(진입점)** | 외부에서 그 시스템을 쓸 때 두드리는 공식 대문. eval_analyzer 의 대문은 `evaluate()` 함수 하나다. |
| **스텁(stub)** | "자리만 잡아둔 미구현 함수". 호출하면 `NotImplementedError`(아직 안 만들었음) 에러를 낸다. 설계상 나중에 채워 넣으라고 비워둔 곳. |
| **멱등(idempotent)** | 같은 작업을 몇 번을 반복해도 결과가 한 번 한 것과 같음. 재실행해도 데이터가 중복으로 쌓이지 않는 안전한 성질. |
| **persist** | "DB 에 저장할까?" 스위치. `persist=False` = 계산만 하고 저장은 안 함(미리보기). |
| **conn 주입** | DB 연결(connection)을 함수 밖에서 만들어 인자로 넣어주는 것. 같은 함수를 "다른 DB 파일"에 쓰게 만드는 기법. 이 프로젝트의 핵심 트릭이다(§5.2). |
| **환경변수(env)** | 프로그램 실행 전에 밖에서 정해주는 설정값. 코드 수정 없이 동작을 바꿀 수 있다. 예: `EVAL_DB_PATH=D:\eval.db`. |
| **YAML** | 사람이 읽기 쉬운 설정 파일 형식. eval_analyzer 는 판정 기준(임계값·룰)을 전부 YAML 로 밖에 빼두었다. |
| **비동기 / 데몬 스레드** | 오래 걸리는 일을 뒤에서 몰래 처리하게 하는 것. 사용자는 기다리지 않는다. 코멘트 → eval DB 복사가 이 방식이다. |
| **cpk** | 공정능력지수. 규격(USL/LSL) 대비 분포가 얼마나 여유 있는지의 지표. 낮을수록 위험. |
| **선례(precedent)** | 과거에 비슷한 fail item 에 대해 엔지니어가 남긴 판단·코멘트 기록. 이 시스템에서 "학습 데이터"에 가장 가까운 개념. |
| **감사 로그(audit log)** | 누가 언제 무엇을 했는지 남기는 기록. 실패 추적용. |

## 3. 평가 엔진의 동작 원리 — L0~L6 여섯 단계

`evaluate(run_input)` 하나를 부르면 아래 6단계가 순서대로 돈다 ([api.py:39-57](../../eval_analyzer/eval_engine/api.py#L39-L57)).
**비유**: 건강검진과 같다 — 접수(L0) → 측정(L1) → 정밀지표(L2) → 소견 판독(L3) → 등급 판정(L4) → 처방 코멘트(L5) → 결과지 출력(L6).

| 단계 | 파일 | 무엇을 하나 (쉬운 설명) | DB 를 읽나? |
|---|---|---|---|
| **L0 ingest** | [pipeline/ingest.py:370](../../eval_analyzer/eval_engine/pipeline/ingest.py#L370) | 입력 데이터(raw_df)를 받아 "fail 난 item(case)" 목록을 만든다. fail 판별 = `FAILTNO == 그 item 의 TNO` 인 시료의 BIN 을 fail bin 으로 잡음. item 이름 정규화, `case_id`(자연키 해시) 생성 | ✗ |
| **L1 metrics** | [pipeline/metrics.py:47](../../eval_analyzer/eval_engine/pipeline/metrics.py#L47) | cpk/평균/표준편차/수율/이봉성(bimodality) 등 **요약 통계** 계산. 원시(per-DUT) 값은 저장하지 않음 | ✗ |
| **L2 features** | [pipeline/features.py:161](../../eval_analyzer/eval_engine/pipeline/features.py#L161) | 판정용 정밀 지표 22종 — robust 산포, outlier 비율, 왜도/첨도, spec 여유, 웨이퍼 공간 패턴(edge/center/gradient), site 편차 등 | ✗ |
| **L3 signatures** | [pipeline/signatures.py:51](../../eval_analyzer/eval_engine/pipeline/signatures.py#L51) | **룰 판독**: `rules/signatures.yaml` 의 고장모드 15종(WIDE_DISTRIBUTION, EDGE_FAIL, LOW_CPK …)을 `rules/thresholds.yaml` 임계값과 비교해 "발화한 signature" 목록 산출 | ✗ |
| **L4 status** | [pipeline/status.py:27](../../eval_analyzer/eval_engine/pipeline/status.py#L27) | 발화 signature 들의 심각도를 종합해 **최종 등급**(CRITICAL/MAJOR/MINOR/MONITOR/OK) + 신뢰도(confidence) 결정 | ✗ |
| **L5 recommend** | [pipeline/recommend.py:14](../../eval_analyzer/eval_engine/pipeline/recommend.py#L14) | **선례검색 + 코멘트 생성**: 과거 DB 에서 비슷한 item 의 사람 코멘트를 찾아, 룰 골격 문장에 "(과거 사례 N건: …)" 으로 붙인다. LLM 이 켜져 있으면 자연어로 합성(현재는 스텁이라 항상 템플릿) | **✓ (유일)** |
| **L6 present** | [pipeline/present.py:51](../../eval_analyzer/eval_engine/pipeline/present.py#L51) | 결과 dict 직렬화 + (`persist=True` 일 때만) eval.db 에 적재 | 쓰기만 |

**여기서 가장 중요한 관찰 (→ 02 문서의 주제)**:

- L0~L4(판정)는 **그 회차 데이터와 YAML 임계값만** 쓴다. **과거 DB 를 전혀 읽지 않는다.**
- 과거 DB 를 읽는 곳은 **L5 선례검색 단 한 곳**이고, 그 결과는 **코멘트 문장에만** 쓰인다.
- 즉 이 엔진은 "규칙 기반 판정기 + 선례 코멘트 인용기"이지, 스스로 학습하는 ML 모델이 아니다.

### 3.1 선례검색은 어떻게 동작하나 ([store.py:470-518](../../eval_analyzer/eval_engine/store.py#L470-L518))

1. SQL 로 후보를 좁힌다: 같은 `value_type`(전압/전류/코드 등 측정값 종류) + (있으면) 같은 `family_product`.
   **bin 은 매칭 조건이 아니다** (더 폭넓게 참고하기 위한 의도적 설계).
2. Python 에서 item 이름 유사도를 계산한다: `difflib.SequenceMatcher`(문자열 겹침 비율) **≥ 0.70** 만 통과
   ([store.py:508-509](../../eval_analyzer/eval_engine/store.py#L508-L509), 임계값 [config.py:30](../../eval_analyzer/eval_engine/config.py#L30)).
3. 정렬: **사람 코멘트(human_comment)가 있는 선례 우선** → 유사도 내림차순 ([store.py:515-517](../../eval_analyzer/eval_engine/store.py#L515-L517)).
4. 자기 자신(현재 평가 중인 case)은 제외. DB 파일이 아예 없으면 조용히 빈 목록(에러 아님, [store.py:481-482](../../eval_analyzer/eval_engine/store.py#L481-L482)).

> **주의점**: 이 검색은 임베딩/AI 유사도가 아니라 **문자 겹침 비율**이다. item 이름 표기가 다르면
> (예: 접두어·언더스코어 차이) 같은 항목이라도 못 찾을 수 있고, 반대로 이름만 비슷한 다른 항목이 잡힐 수 있다.
> 또한 호출부([precedent_client.py:21-26](../../eval_analyzer/eval_engine/precedent_client.py#L21-L26))가 `limit` 없이 부르므로 **매칭된 선례 전부**가 반환된다.

### 3.2 코멘트는 어떻게 만들어지나 ([recommend.py:18-27](../../eval_analyzer/eval_engine/pipeline/recommend.py#L18-L27))

```
[룰 골격 문장]  ←  signatures.yaml 의 action_ko (예: "산포 원인 확인 필요")
      +
[선례 인용]     ←  "(과거 사례 3건: site 편차로 재측정 / trim 재조정 후 회복 / …)"
```

- LLM 이 켜져 있으면 위 재료로 프롬프트를 만들어 한 문장으로 합성하지만
  ([recommend.py:45-54](../../eval_analyzer/eval_engine/pipeline/recommend.py#L45-L54)),
  `llm_client.complete()` 가 **미구현 스텁**이라 현재는 **항상 템플릿 방식**이다.
- 선례 인용은 반환된 **모든** human_comment 를 `" / "` 로 이어붙인다 — 상한이 없다(→ 02 문서 §4.5 리스크).

## 4. eval.db 스키마 — 17개 테이블 한눈에

정본: [store.py:17-117](../../eval_analyzer/eval_engine/store.py#L17-L117) `SCHEMA` + [docs/DB_SCHEMA.md](../../eval_analyzer/docs/DB_SCHEMA.md).
설계 원칙: 원시(per-DUT) 데이터 저장 금지, JSON 컬럼 금지(전부 정규화).

```
[기준정보]                         [사건 기록]                    [판정·판단 근거]
product_master  제품 마스터    ┌── ingest_run   실행 1회 기록      raw_metrics  요약통계(cpk 등)
item_master     item 마스터    │   run_case     실행↔case 연결     features     판정지표 22종
item_alias      이름 별칭      └── fail_case ◀─ 사건 1건(핵심)     evaluation   엔진 판정 결과
item_spec       규격(USL/LSL)                    │                 eval_evidence 판정 근거
bin_taxonomy    bin 의미                         │                 case_signature 발화 signature
                                                 │                 eval_precedent 인용한 선례 이력
[사람의 답 — "학습 데이터"의 핵심]                │
label        사람 판정+코멘트  ◀────────────────┤   [버전 관리]
case_outcome 조치와 결과       ◀────────────────┘   engine_version_registry 룰 버전 기록
```

| 그룹 | 테이블 | 이 시스템에서의 의미 |
|---|---|---|
| 사건 | `fail_case` | "어느 제품·lot 의 어느 item 이 어느 bin 으로 fail" — 모든 것의 중심 키(`case_id`) |
| 통계 | `raw_metrics`, `features` | 엔진이 계산한 숫자들. **features 는 임계값 재보정(calibrate)의 재료** |
| 엔진의 답 | `evaluation`, `case_signature`, `eval_evidence` | 엔진이 내린 판정과 그 근거 |
| **사람의 답** | **`label`**, **`case_outcome`** | 엔지니어의 판정(human_status)·원인 분류(root_cause_category)·코멘트(human_comment)·조치/결과(action/result). **선례검색이 소비하는 원료이자, 룰 정확도 검증의 정답지** |
| 이력 | `eval_precedent` | "이 판정 때 어떤 선례를 인용했나" 기록 |

**저장 게이팅**: 모든 case 가 저장되는 게 아니다. `persist=True` 여도
**yield fail(fail_count>0) 이거나 cpk<cpk_warn 인 case 만** 저장된다
([present.py:11-22](../../eval_analyzer/eval_engine/pipeline/present.py#L11-L22) `should_store`). "정상인 item" 은 쌓이지 않는다.

## 5. 연동 접점 2곳 — 실제 코드 흐름

### 5.1 접점 ① ai_comment.py — "AI Comment 컬럼" (읽기 방향)

**언제**: 세션 옵션 `webreport_options.ai_comment` 가 켜진 세션의 리포트를 **처음 만들 때(콜드 빌드) 1회**
([web_report/service.py:112-117](../../web_report/service.py#L112-L117)). 캐시에 있으면 호출 안 함.

**무엇을 넘기나**:
- 세션 메타(product_name/type/family_product/revision/lot/wafer) — family_product 가 없으면 `*_ETC` 폴백
  ([ai_comment.py:27-33](../../web_report/ai_comment.py#L27-L33))
- 소스 파일별 **원시 측정값 전체**를 엔진 정본 레이아웃(raw_df: 메타 7컬럼 + item 컬럼, 메타 6행 + 측정행)으로 재조립
  ([ai_comment.py:51-72](../../web_report/ai_comment.py#L51-L72))

**호출**: `evaluate({"meta":…, "raw_df":…}, persist=False)` ([ai_comment.py:153](../../web_report/ai_comment.py#L153))

> **persist=False 의 의미**: 평가 결과를 eval.db 에 **저장하지 않는 미리보기 모드**.
> 덕분에 여러 컴퓨트 워커가 동시에 돌아도 DB 충돌이 없고, eval_analyzer 소유 DB 를 오염시키지 않는다.
> 대신 — 이게 02 문서의 핵심인데 — **판정 재료(features)도 전혀 쌓이지 않는다.**

**결과 표시**: case 들을 IssueTable 행 키로 매핑해 `[STATUS] 코멘트` 텍스트를 **읽기 전용 "AI Comment" 컬럼**에 표시
([ai_comment.py:110-130](../../web_report/ai_comment.py#L110-L130), [tabs/issue_table.py:36](../../web_report/tabs/issue_table.py#L36)).
Honey 클라이언트의 "AI Comment" 체크박스는 현재 비활성(검증 후 활성 예정, docs/13 §7).

### 5.2 접점 ② eval_export.py — "사람 코멘트 내보내기" (쓰기 방향)

**언제 (3개 트리거, 저장 즉시·비동기·멱등)**:
1. 세션 업로드 직후 ([web_report/ingest.py:169-176](../../web_report/ingest.py#L169-L176))
2. IssueTable 코멘트 저장 시 ([web_report/service.py:622-628](../../web_report/service.py#L622-L628))
3. ETC item 추가/삭제 시 ([web_report/service.py:448-454](../../web_report/service.py#L448-L454))

매번 **세션 전체 코멘트 상태를 통째로 다시 적재**한다(멱등 — 재실행해도 중복 없음,
[eval_export.py:213-341](../../web_report/eval_export.py#L213-L341)). 백그라운드 데몬 스레드로 돌아 사용자를 기다리게 하지 않는다
([eval_export.py:360-366](../../web_report/eval_export.py#L360-L366)).

**어디에 쓰나**: eval_analyzer 소유 DB 가 아니라 **서버 소유 별도 파일** `REPORT_EVAL_DB_PATH`
(기본 `DB/pe/report/eval/eval.db`, [server/config.py:25](../../server/config.py#L25)).
엔진의 저장 함수(store CRUD)를 그대로 재사용하되, **conn 주입**으로 대상 DB 파일만 바꾼다
([eval_export.py:54-73](../../web_report/eval_export.py#L54-L73) `open_conn`). 스키마는 엔진과 동일한 17테이블.

**무엇이 기록되나** (코멘트가 달린 case 당):

| 테이블 | 채워지는 값 | 출처 |
|---|---|---|
| `ingest_run` | product/lot/source_file/session_id, `ingested_by="web_report"` | 세션 |
| `product_master` | product_name/type/family_product/revision | 세션 메타 |
| `item_master`, `item_alias` | item 정규화 이름·분류·단위 | 엔진 규칙 재사용 |
| `item_spec` | USL/LSL (있을 때) | honeyform 테이블 |
| `fail_case` | case_id (**wafer_number=None — lot 수준**), item, bin | row_key 파싱 |
| `raw_metrics` | cpk/mean/stdev + (fail bin 이면) fail_count/yield — **best effort** | web_report 통계 재계산 ([eval_export.py:160-203](../../web_report/eval_export.py#L160-L203)) |
| **`label`** | **`human_comment` = "[PTE] …\n[개발] …" 병합 1행**, labeler="web_report", reviewer=마지막 편집자 | IssueTable 코멘트 ([eval_export.py:311-314](../../web_report/eval_export.py#L311-L314)) |

> **"병합 label 1행"**: PTE comment 와 개발 comment 를 따로 넣지 않고 한 문자열로 합쳐
> case 당 label **1행만** 유지한다(기존 web_report label 삭제 후 재삽입 — 멱등).

**기록되지 않는 것**: `human_status`(사람 판정 등급), `root_cause_category`(원인 분류),
`outcome_action/result`(조치/결과), `features`, `evaluation` — 전부 None/미기록. (→ 02 문서 §4)

**실패 처리**: 예외는 격리되어 업로드/편집을 죽이지 않고, 감사 로그(`action="eval_export", result="error"`)에 남는다
([eval_export.py:344-357](../../web_report/eval_export.py#L344-L357)). 관리자 대시보드 Eval DB 탭이 최근 7일 실패 건수를 배지로 보여준다
([server/admin_panel/eval_admin.py:37-49](../../server/admin_panel/eval_admin.py#L37-L49)).

### 5.3 IssueTable 코멘트는 어디에 저장되나 (export 이전 단계)

1. 사용자가 세션 상세 IssueTable 에서 "PTE comment"/"개발 comment" 입력
2. `POST /pe/report/session/<sid>/web_report/issue_table/comments`
   ([routes_webreport.py:499-525](../../server/report/routes_webreport.py#L499-L525)) — CSRF + 편집 권한 검사
3. **report.db** 의 `report_webreport_edit` 테이블에 저장
   ([server/database/core.py:220-228](../../server/database/core.py#L220-L228)):
   `(session_id, kind="issue_comment", item_key=row_key+구분자+컬럼, value=코멘트, updated_by=계정)`
4. 위 §5.2 의 export 가 이것을 읽어 eval DB `label` 로 복사

> 즉 코멘트의 **1차 저장소는 report.db**(웹 편집용), **2차 저장소가 eval DB**(선례용)다.
> report.db 쪽에는 item 이름·bin 이 row_key 문자열 안에만 있고, TNO/단위/규격/제품군 같은
> 컨텍스트 메타는 저장되지 않는다 — 이 메타가 실제 값으로 붙는 곳은 export 시점의 eval DB 쪽이다.

## 6. db_input — 초기 선례를 손으로 넣는 길 (현재 상태)

운영 파이프라인과 별개로, **과거 평가 사례를 선례 DB 에 미리 채워 넣기 위한** 오프라인 도구다
([db_input/CLAUDE.md](../../eval_analyzer/db_input/CLAUDE.md)).

| 진입점 | 입력 | 동작 |
|---|---|---|
| `python db_input/import_csv.py <csv>` | **정형 CSV** (컬럼 20개, 필수 6개: product_name/product_type/family_product/item_name/value_type/bin) | 제품군별 `output/<type>_<family>.db` 로 분리 적재. `--to-eval-db` 옵션이면 운영 eval.db 하나로 통합 적재 ([import_csv.py:214-226](../../eval_analyzer/db_input/import_csv.py#L214-L226)) |
| `python db_input/import_text.py --json/--input` | 스키마에 맞는 JSON rows / 텍스트 | 검증(`--preview`) → CSV 변환 → 저장 (저장은 import_csv 에 위임) |
| `run_import.bat` | (윈도우 더블클릭) | 파일 선택창 → import_csv 실행 |

잘 되어 있는 점:
- 엔진의 item 정규화 규칙을 그대로 재사용 → 나중에 선례검색 매칭이 어긋나지 않음
- `make_case_id` 자연키 upsert → **재실행해도 중복 없음(멱등)**
- average/stdev/USL/LSL 이 있으면 cpk 를 계산해 raw_metrics 까지 채움
- `human_comment`/`human_status`/`root_cause_category`/`outcome_*` 컬럼까지 받는다 —
  즉 **CSV 로는 label 을 완전체로 넣을 수 있다** (web_report export 보다 오히려 완전)

부족한 점 (→ 05 문서에서 상세):
- **"복붙한 문서 → 자동 파싱"은 미구현**. LLM 추출 훅 `extract_rows_from_text` 는
  `NotImplementedError` 스텁 ([ai_extract.py:137-142](../../eval_analyzer/db_input/ai_extract.py#L137-L142)).
  현재는 사람이 CSV 스키마에 맞게 직접 정리해야만 넣을 수 있다.
- 검수(preview) UI 없음 — CLI 텍스트 출력뿐.
- 실행 중 `config.DB_PATH` 를 덮어쓰는 단발 스크립트 전제 ([import_csv.py:107-108](../../eval_analyzer/db_input/import_csv.py#L107-L108)) — 서버 프로세스 안에서 그대로 부르면 위험.

## 7. 한 장 요약 — 데이터가 흐르는 3개의 길

```
길 A. 평가(읽기):   업로드 → 콜드 빌드 → ai_comment → evaluate(persist=False)
                    → [L5 만 REPORT_EVAL_DB 선례 조회] → AI Comment 컬럼 표시
                    ※ 결과는 캐시에만 — DB 에 아무것도 남지 않음

길 B. 적재(쓰기):   IssueTable 코멘트 입력 → report.db(report_webreport_edit)
                    → 비동기 eval_export → REPORT_EVAL_DB (fail_case + raw_metrics + label)
                    ※ human_comment 만. human_status/root_cause/outcome 은 비어 있음

길 C. 초기 적재:    과거 사례 CSV → db_input/import_csv → 선례 DB
                    ※ label 완전체 가능. 단, CSV 를 사람이 손으로 만들어야 함
```

길 B 가 쌓은 human_comment 를 길 A 의 선례검색이 인용한다 — **이 뼈대는 이미 연결되어 있고 작동 구조가 맞다.**
다만 "쌓일수록 엔진이 좋아지는가" 라는 질문에는 몇 가지 끊어진 고리가 있다. → [02_상관관계_분석.md](02_상관관계_분석.md)
