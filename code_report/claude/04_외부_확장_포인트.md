# 04. 외부 확장 포인트 — eval_analyzer 를 고치지 않고 이을 수 있는 것들

> 02 문서에서 찾은 "끊어진 고리"를 **report_server 쪽 코드 추가만으로** 잇는 방법을 정리했습니다.
> 전부 **제안(설계 스케치)**이며, 이번에 코드는 변경하지 않았습니다.
> 난이도: ●낮음 / ●●중간 / ●●●높음 (서버 개발 기준).

## 0. 대원칙 — import 2곳 규약을 지키면서 확장하는 방법

현행 규약: eval_engine import 는 [web_report/ai_comment.py](../../web_report/ai_comment.py) 와
[web_report/eval_export.py](../../web_report/eval_export.py) **2곳만** (docs/13 §2, CLAUDE.md 규칙 #8).

따라서 아래 모든 확장은 다음 중 하나의 형태를 취한다:

1. **기존 2개 파일 내부를 확장** — 새 함수를 이 두 파일 안에 추가 (규약 자동 준수)
2. **이 두 파일을 경유** — 새 코드(라우트·UI·admin)는 eval_engine 을 직접 import 하지 않고
   `eval_export.…` / `ai_comment.…` 의 함수만 호출 (admin Eval DB 탭이 이미 이 패턴:
   [eval_admin.py](../../server/admin_panel/eval_admin.py) 가 `eval_export.open_conn/db_path` 재사용)
3. **환경변수만 조정** — 코드 0줄 (E-7)

또 하나의 핵심 지렛대 — **엔진 설정이 전부 env override 가능**하다는 점
([eval_engine/config.py](../../eval_analyzer/eval_engine/config.py)):

| env | 기본 | 우리가 쓸 수 있는 용도 |
|---|---|---|
| `EVAL_DB_PATH` | eval_analyzer/data/eval.db | 엔진의 읽기(선례)·쓰기(persist) 대상을 **서버 소유 DB 로 전환** |
| `EVAL_RULES_DIR` | eval_engine/rules | 룰 YAML 을 **서버 소유 폴더로 분리** → 동결 폴더를 안 건드리고 calibrate 반영 가능 |
| `EVAL_LLM_*` | off | LLM 코멘트 합성 켜기 (단, complete() 구현은 03 문서 R-2 필요) |
| `EVAL_PRECEDENT_BACKEND` | sql | `rag` 로 전환 (E-6 구현 후) |

## E-1. IssueTable 라벨 입력 UI — "사람의 정답"을 받기 시작한다  ●●

**목적**: 02 문서 끊어짐 ② 해소. label 을 human_comment 반쪽짜리에서 완전체로.

**전제(확인됨)**: 엔진의 [store.insert_label](../../eval_analyzer/eval_engine/store.py#L418) 은
`human_status, root_cause_category, human_comment, labeler, reviewer, label_quality` 등을 이미 받는다.
[store.insert_case_outcome](../../eval_analyzer/eval_engine/store.py#L431) 도 `action/condition/result` 를 받고
어휘 검증까지 해 준다. **엔진 수정 0.**

**설계 스케치**:

1. **UI**: IssueTable 행에 선택 입력 3개 추가 (기존 comment 편집 UX 재사용)
   - `판정` 드롭다운: CRITICAL/MAJOR/MINOR/MONITOR/OK (DB_SCHEMA §10 status 어휘)
   - `원인` 드롭다운: equipment/process/design/spec/unknown
   - `조치/결과` 드롭다운 2개: outcome_taxonomy.yaml 의 action 10종 / result 7종
     (어휘 목록은 서버가 하드코딩하지 말고 **export 시 엔진 검증에 맡기고**, UI 목록은
     설정/상수로 — 어휘 불일치 시 export 가 에러 감사로그를 남기므로 탐지 가능)
2. **저장**: 기존 코멘트와 동일하게 `report_webreport_edit` 에 새 kind (예: `issue_label`) 로 저장
   — 편집 저장의 기존 규약(세션 편집 DB 가 진실, autoSave 채널 합류) 그대로.
3. **export**: [eval_export.py](../../web_report/eval_export.py) 의 `export_session_comments` 확장 —
   `_collect_comments` 가 label kind 도 수집, `insert_label` 호출 시 `human_status=…,
   root_cause_category=…` 를 채우고, outcome 이 있으면 `insert_case_outcome` 추가 호출.

**주의점**:
- 입력 강제는 금물 — 전부 **선택 입력**으로. (현장 부담이 크면 아무도 안 쓴다. 코멘트를 쓰는
  김에 클릭 2번으로 등급/원인만 남겨도 정답지가 쌓인다.)
- 세션 meta 에 wafer 개념이 있는 경우에도 export 는 현재 **lot 수준 case**(wafer_number=None,
  [eval_export.py:228-231](../../web_report/eval_export.py#L228-L231))다. E-3 의 features(wafer 수준)와
  case_id 가 달라질 수 있으므로, 나중에 "사람 정답 vs 엔진 판정" 성적표(03 문서 R-4)를 만들 때는
  case_id 직접 조인이 아니라 (product, lot, item, bin) 키 조인으로 비교하도록 설계할 것.

**효과**: 룰 정확도 측정·calibrate 검증·false_fail 통계의 **정답지가 이날부터 쌓이기 시작**한다.
이 항목이 모든 "엔진이 좋아지는 미래"의 출발점이라 우선순위 최상.

## E-2. AI Comment 채택/수정 신호 기록  ●

**목적**: 02 문서 끊어짐 ③ 해소. 엔진 정확도의 가장 값싼 측정 지표 확보.

**전제(확인됨)**: label 스키마에 `engine_comment_accepted`, `comment_modified` 컬럼이 이미 있고
`insert_label` 이 받는다 ([store.py:99-110](../../eval_analyzer/eval_engine/store.py#L99-L110)).

**설계 스케치** (두 단계, 작게 시작):
- **1단계(코드만, UI 없음)**: export 시점에 자동 판정 — 그 행에 AI Comment 가 표시되어 있었고
  사람 코멘트도 있으면 `comment_modified=1` 성격의 신호로 기록. (엄밀하진 않지만 0 보다 낫다)
- **2단계(UI)**: AI Comment 셀에 👍/👎 (또는 "채택" 버튼 → PTE comment 로 복사) 추가,
  클릭을 `report_webreport_edit` kind=`ai_feedback` 으로 저장 → export 시 `engine_comment_accepted` 반영.

**주의점**: AI Comment 는 콜드 빌드 캐시에 묶여 있어 ([service.py:112-117](../../web_report/service.py#L112-L117))
"당시 사용자가 본 AI 코멘트 원문"을 함께 저장해 두어야 나중에 비교가 성립한다
(payload 의 셀 텍스트를 피드백 레코드에 복사 저장 권장).

**효과**: "AI Comment 채택률" 이라는 단일 숫자로 엔진 개선 효과를 추적 가능해진다 (06 문서 KPI).

## E-3. features/evaluation 축적 — calibrate 의 재료 만들기  ●●●

**목적**: 02 문서 끊어짐 ① 해소. "쌓일수록 판정이 좋아지는" 유일한 공식 경로(calibrate)에 연료 공급.

**먼저, 안 되는 방법 (확인됨)**: AI Comment 결과 dict 를 재사용해 features 를 저장하는 것은 **불가**.
`to_result` 가 돌려주는 것은 status/comment/evidence 요약뿐, L2 features 22종 전체가 담기지 않는다
([present.py:51-78](../../eval_analyzer/eval_engine/pipeline/present.py#L51-L78)).
features 가 DB 에 기록되는 유일한 경로는 `evaluate(persist=True)` → `present.persist`
([present.py:25-48](../../eval_analyzer/eval_engine/pipeline/present.py#L25-L48)) 다.

**되는 방법 (엔진 무수정)**: `present.persist` 는 `store.get_conn()` = `EVAL_DB_PATH` 가 가리키는
파일에 쓴다. 서버 기동 시 **`EVAL_DB_PATH` = `REPORT_EVAL_DB_PATH`** 로 지정하면
`evaluate(persist=True)` 가 **서버 소유 DB** 에 features/evaluation/eval_precedent 를 쌓는다 — 코드 수정 없이 대상만 전환.

**설계 스케치 (권장안)**:
- 콜드 빌드의 `ai_comment` 호출은 **persist=False 유지** (동시성·미리보기 규약 그대로).
- 대신 **eval_export 의 백그라운드 스레드**(이미 세션당 1회, 저동시성)에 env 게이트로 추가:
  ```
  # eval_export.py 안 (개념 스케치 — import 2곳 규약 준수)
  if config.REPORT_EVAL_PERSIST_FEATURES:            # 새 env, 기본 off
      evaluate({"meta": meta, "raw_df": raw_df}, persist=True)   # EVAL_DB_PATH=서버 DB 전제
  ```
  raw_df 재조립은 `ai_comment._table_to_raw_df` 재사용(이미 서버 코드).
- 트리거는 "업로드 1회당 1번"이면 충분 (편집 때마다 재평가할 필요 없음 — features 는 데이터의 함수).

**주의점 (정직하게)**:
- **docs/13 §4 규약 개정 필요**: "서버는 persist=False" 문구가 있다. 목적(eval_analyzer 소유 DB 보호)은
  `EVAL_DB_PATH` 를 서버 소유 파일로 돌리는 순간 충족되지만, **규약 문서를 고치고 외부 담당자와 합의**하고
  진행해야 한다. 몰래 바꾸면 안 되는 항목.
- **동시성**: 여러 세션이 동시에 업로드되면 SQLite 동시 쓰기 경합 가능. eval_export 는 데몬 스레드라
  세션 간 병렬이 있을 수 있음 → 서버 쪽에 간단한 직렬화 락(스레드 Lock 1개) 권장.
- **persist=True 는 L0 에서 마스터 upsert 도 수행** ([api.py:35-39](../../eval_analyzer/eval_engine/api.py#L35-L39)) —
  같은 DB 에 export 가 쓰는 item_master 와 자연스럽게 합류(정규화 규칙이 같아서 안전)하지만,
  기록량이 늘어난다는 점은 인지.
- **저장 게이팅 동일**: yield fail 또는 cpk<cpk_warn case 만 저장 ([present.py:11-22](../../eval_analyzer/eval_engine/pipeline/present.py#L11-L22)).
  calibrate 표본도 이 기준으로 쌓인다 (정상 item 의 분포는 안 쌓임 — calibrate 목적상 큰 문제는 아니나 표본 편향 인지).

**효과**: item_class 당 features 가 30건 이상 모이는 시점부터 calibrate(03 문서 R-5 절차와 세트)로
임계값을 데이터에 맞춰 개정할 수 있다 — **판정도 쌓일수록 좋아지는 두 번째 축 완성.**

**목적**: 쌓이는 데이터의 **품질 관리** 창구. (양보다 질 — 선례 코멘트에 오타·무의미 텍스트가 쌓이면

**전제(확인됨)**: admin Eval DB 탭이 이미 존재하고 `eval_export.open_conn/db_path` 를 재사용한다
([eval_admin.py](../../server/admin_panel/eval_admin.py) — overview/최근실패배지/case 삭제).

**설계 스케치** (기존 탭에 붙일 위젯):

  "정답지 커버리지"를 한눈에.
- **라벨 검수 리스트**: 최근 export 된 label 을 훑어보고 품질 낮은 코멘트(한 글자, 테스트 입력 등)를

- **선례 활용도**: E-3 적용 후에는 `eval_precedent` 테이블에서 "AI Comment 가 선례를 인용한 비율(히트율)"

## E-6. RAG 선례검색 백엔드 — 계약된 우리 몫  ●●●

**성격이 특수한 항목**: 구현 위치(`precedent_client._rag_search`)는 eval_analyzer **내부**지만,
핸드오프 문서가 "**report_server 담당자가 이 한 함수만 구현**하라"고 이미 계약해 두었다
([docs/PRECEDENT_RAG_HANDOFF.md](../../eval_analyzer/docs/PRECEDENT_RAG_HANDOFF.md) — 교체 지점 단 하나,
다른 파일 수정 금지, endpoint 하드코딩 금지). 즉 **승인 절차만 밟으면 우리가 구현하는 항목**이다.

**설계 스케치**:
- 임베딩 검색 서비스는 **eval_analyzer 밖**(report_server 측 또는 독립 서비스)에 두고,
  `_rag_search` 는 `config.EVAL_PRECEDENT_RAG_ENDPOINT` 로 HTTP 호출만 하는 얇은 클라이언트로 구현.
- 반환 계약 3키(action/result/human_comment) + 관련도 내림차순 + top-k(`EVAL_PRECEDENT_RAG_TOPK`, 기본 5) 준수.
- 색인 대상: label.human_comment + item_canonical(+value_type/family 스코프) — 핸드오프 §5 가이드 그대로.

**언제 할 것인가**: **서두를 필요 없음.** difflib 검색의 한계(이름 표기 편차)가 실제로 문제 되려면
선례가 수백 건은 쌓여야 한다. 그 전까지는 SQL 백엔드 + item_alias 보강으로 충분. → 06 문서 Phase 3.
(참고: RAG 는 top-k 상한이 있어 R-1(코멘트 폭발) 문제도 함께 풀리지만, 그것 때문에 앞당길 필요는 없다 —
R-1 은 한 줄짜리 요청이다.)

## E-7. 코드 0줄 — 환경변수 배선과 운영 절차  ●

당장 코드 없이 결정·문서화만으로 할 수 있는 것들:

1. **선례 소비 배선 확정**: eval_analyzer 를 독립 실행(콘솔 testbench, 챗봇 등)할 때
   `EVAL_DB_PATH=<REPORT_EVAL_DB_PATH>` 로 지정하면 **서버가 쌓은 코멘트 DB 를 그대로 선례로 읽는다**
   (docs/13 §9 에 이미 예정된 사용법). 운영 스크립트/문서에 이 배선을 명시.
2. **rules 폴더 분리 검토**: calibrate 는 `thresholds.yaml` 을 **재작성**한다 — 동결 폴더 안의 파일이다.
   `EVAL_RULES_DIR` 를 서버 소유 폴더(예: `DB/pe/report/eval/rules/`, 원본 복사본)로 빼면
   동결 침해 없이 보정 결과를 반영·버전 관리할 수 있다. (원본과의 drift 관리 규칙 필요 — 03 문서 R-5 와 함께 협의)
3. **백업 편입**: `REPORT_EVAL_DB_PATH` 파일을 기존 DB 백업 사이클에 포함하는지 확인/편입.
   이 파일이 곧 "학습 자산"이 되므로 유실 대비가 필요하다.
