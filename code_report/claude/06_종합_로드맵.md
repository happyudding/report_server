# 06. 종합 로드맵 — 운영 · 엔진 품질 · DB 적재 3관점 실행 계획

> 01~05 문서의 진단·설계를 **실행 순서**로 엮었습니다. 항목 번호는 앞 문서를 가리킵니다
> (R-x = 03 문서 외부 담당자 요청, E-x = 04 문서 서버 측 확장, v0~v2 = 05 문서 db_input).
> 코드는 변경하지 않았으며, 전부 제안입니다.

---

## 1. 우선순위를 정한 논리

1. **정답지(label)와 재료(features)는 이르면 이를수록 좋다** — 데이터는 소급이 안 된다.
   오늘 시작하지 않은 축적은 6개월 뒤에도 0건이다. → E-1, E-3 이 최우선.
2. **쌓기 전에 "쌓을수록 나빠지는 지점"부터 막는다** — R-1(선례 인용 상한)은 한 줄짜리
   요청이므로 대량 적재(v0) 전에 끝내는 것이 순서다.
3. **콜드스타트는 v0(LLM 불필요)로 즉시** — 외부 담당자 일정(R-2/R-3)에 묶이지 않는 경로를 먼저 간다.
4. **측정 없이 개선 없다** — 채택률(E-2)·성적표(R-4)가 있어야 "엔진이 좋아졌다"를 말할 수 있다.
5. **고급 기능(LLM 합성·RAG)은 데이터가 모인 뒤에** — 빈 DB 위의 RAG 는 의미가 없다.

의존 관계 한눈에:

```
R-1(인용 상한) ──┬──▶ v0 대량 적재 ──▶ 선례 인용 활성화(즉시 체감)
                 │
E-1(라벨 UI) ────┼──▶ label 정답지 축적 ──▶ R-4(성적표) ──▶ R-6(판정 개선 논의)
E-2(채택 기록) ──┤                                   ▲
E-3(features) ───┴──▶ calibrate 재료 축적 ──▶ R-5(보정 절차) ─┘
R-2(LLM) ────────────▶ 코멘트 자연어 합성 (선례 많을수록 효과↑)
E-6(RAG) ────────────▶ 검색 품질 (선례 수백 건 이후에 의미)
```

## 2. Phase 별 실행 계획

### Phase 1 — 지금 시작 (0~1개월): "쌓기 시작 + 안전장치"

| # | 항목 | 관점 | 누가 | 비고 |
|---|---|---|---|---|
| 1 | **R-1** 선례 인용 상한(top-k) 요청 전달 | 운영 안정 | 외부 담당자 (요청서: 03 문서) | 한 줄 수정 — 대량 적재 전 필수 |
| 2 | **v0** db_input 로컬 도구 (엑셀 복붙→매핑→검증→적재) | DB 적재 | 우리 | LLM 불필요, 뒷단 전부 재사용 (05 문서) |
| 3 | **E-1** IssueTable 라벨 입력 UI (status/원인/조치 선택 입력) | DB 적재·품질 | 우리 | 정답지 축적 시작 — 최우선 |
| 4 | **E-2** AI Comment 채택/수정 기록 (1단계: 자동 신호) | 엔진 품질 측정 | 우리 | 난이도 낮음 |
| 5 | **E-7** 배선·백업: REPORT_EVAL_DB 백업 편입, EVAL_DB_PATH 소비 배선 문서화 | 운영 | 우리 | 코드 0줄 |
| 6 | R-3 **계약 확정** (추출기는 외부 구현 — B 안) + docs/13 갱신 합의 | 거버넌스 | 양측 | 문서 합의만 |

**Phase 1 종료 시 상태**: 과거 선례가 DB 에 들어가 AI Comment 인용이 실제로 동작하고,
새 코멘트·라벨·채택 신호가 매일 쌓이기 시작한다.

### Phase 2 — 축적 가속 (1~3개월): "재료 완성 + 측정 시작"

| # | 항목 | 관점 | 누가 | 비고 |
|---|---|---|---|---|
| 1 | **E-3** features/evaluation 축적 (eval_export 확장 + EVAL_DB_PATH 전환, docs/13 §4 개정 합의) | 엔진 품질 | 우리(+합의) | calibrate 연료 공급 시작 |
| 2 | **R-2** llm_client.complete 구현 + 사내 endpoint 배선 | 엔진 품질 | 외부 담당자 + 우리(인프라) | 코멘트 자연어 합성 |
| 3 | **v1** 자유 서식 LLM 추출 트랙 | DB 적재 | 우리 | R-2 와 같은 LLM 인프라 재사용 |
| 4 | **E-5** admin 검수 대시보드 (label 커버리지·품질 검수·삭제) | 운영·품질 | 우리 | 쌓이는 데이터의 질 관리 |
| 5 | **E-2** 2단계 (👍/👎 UI) | 측정 | 우리 | 채택률 KPI 정식화 |

**Phase 2 종료 시 상태**: label 완전체 + features 가 쌓이고, 코멘트는 LLM 합성으로 읽기 좋아지고,
"채택률" 숫자로 개선을 추적한다.

### Phase 3 — 개선 루프 가동 (3개월+): "쌓인 데이터로 엔진을 실제로 개선"

| # | 항목 | 관점 | 누가 | 비고 |
|---|---|---|---|---|
| 1 | **R-4** 룰 성적표 (엔진 status vs human_status 혼동행렬) | 엔진 품질 | 외부 담당자 | label 이 모인 뒤 착수 |
| 2 | **R-5 + E-7** calibrate 정기 운영 (rules 분리, dry-run, 버전 관리) | 엔진 품질·운영 | 양측 | item_class 당 n≥30 도달 시 |
| 3 | **E-6** RAG 선례검색 (_rag_search 1함수 — 계약된 우리 몫) | 엔진 품질 | 우리(승인 절차) | 선례 수백 건 이후 |
| 4 | **v2** admin "선례 적재" 탭 통합 | DB 적재·운영 | 우리 | v0/v1 파이프라인 이식 |
| 5 | **R-6** 판정 레이어의 label 활용 설계 논의 | 엔진 품질(장기) | 양측 | R-4 데이터 기반으로 |

**Phase 3 종료 시 상태**: "쌓인다 → 측정한다 → 보정한다 → 좋아진다" 루프가 실제로 돈다 —
사용자가 목표한 "DB 가 쌓일수록 정확도가 향상되는 구조"의 완성형.

## 3. 관점별로 다시 보기

### 운영 관점 (안정성·관리)
- 이미 좋은 것: 비동기·멱등 export, 실패 감사로그+admin 배지, DB 소유권 분리 (02 문서 §5)
- 보강: R-1(코멘트 폭발 방지) → E-7(백업·배선 문서화) → E-5(품질 검수 창구) →
  calibrate 운영 절차(R-5)와 rules 사본 버전 관리
- 원칙: **새 접점·규약 변경은 반드시 docs/13 갱신과 함께** (특히 E-3 의 persist 규약 개정)

### 엔진 품질(정확도) 관점
- 단기 체감: 선례 채우기(v0) + 인용 상한(R-1) — AI Comment 가 즉시 유용해짐
- 중기: LLM 합성(R-2) — 나열형 인용이 읽기 좋은 한 문장으로
- 진짜 "학습": features 축적(E-3) → calibrate(R-5) 로 임계값이 데이터를 따라가고,
  label 정답지(E-1) → 성적표(R-4) 로 룰 자체를 검증·개정
- 장기: RAG(E-6), 판정 레이어 논의(R-6)

### DB 적재 관점
- 두 물길을 동시에: **과거분**(v0/v1 대량 적재 — label 완전체 가능) + **현재분**(E-1/E-2 로
  운영 중 자연 축적)
- 질 관리: label_quality 태깅으로 출처 구분(manual/imported), E-5 검수로 저질 데이터 걸러내기
- 유실 대비: REPORT_EVAL_DB 백업 편입 (E-7)

## 4. 성공을 재는 숫자 (KPI 제안)

| KPI | 정의 | 목표 예시 | 어디서 측정 |
|---|---|---|---|
| 선례 보유량 | label.human_comment 있는 fail_case 수 (family 별) | Phase 1 말 family 당 50+ | E-5 대시보드 |
| 정답지 커버리지 | human_status 가 있는 label 비율 | Phase 2 말 30%+ | E-5 대시보드 |
| 선례 히트율 | AI Comment 에 선례가 1건 이상 인용된 case 비율 | 상승 추세 | evaluate 로그 precedent_hits → E-3 후 eval_precedent 집계 |
| AI Comment 채택률 | engine_comment_accepted 비율 | 상승 추세 | E-2 |
| calibrate 가용 클래스 | features n≥30 인 item_class 수 | Phase 3 진입 조건 | features 집계 |
| 판정 일치율 | 엔진 status == human_status 비율 | R-4 성적표의 기준선 → 개선 | R-4 |
| export 실패 | eval_export 실패 건수(7일) | 0 유지 | admin 배지 (이미 있음) |

## 5. 마지막 한 장 요약

> **지금 구조는 "학습하는 시스템"의 그릇까지는 잘 만들어져 있다.**
> 코멘트 선순환(사람 코멘트 → 선례 → AI Comment 인용)은 이미 연결되어 작동 구조가 맞고,
> DB 소유권·경계·멱등성 같은 어려운 부분이 오히려 먼저 풀려 있다.
>
> 끊어진 것은 물길 4개다 — ①판정 재료(features)가 안 쌓이고, ②사람 정답(등급·원인)을 안 받고,
> ③AI 코멘트 피드백을 안 남기고, ④과거 문서를 부어 넣을 깔때기가 미완성이다.
> 넷 모두 eval_analyzer 를 고치지 않고(또는 한 줄 요청으로) 이을 수 있다.
>
> 순서는: **막을 것 먼저(R-1) → 부을 것 붓고(v0) → 받을 것 받기 시작(E-1/E-2/E-3) →
> 그 데이터로 측정(R-4)하고 보정(calibrate)한다.** 이 순서대로면 "DB 가 쌓일수록
> 정확도가 좋아지는 구조"는 구호가 아니라 측정 가능한 사실이 된다.
