1. 결론: 데이터 길은 있지만 학습 루프는 닫혀 있지 않다

현재 시스템에는 “web_report raw로 평가하기”와 “사람 코멘트를 eval 스키마 DB에 복사하기”가 각각 구현되어 있다. 그러나 기본 경로가 서로 다른 DB를 가리키고, AI 기능은 비활성이고, 온라인 평가는 무기록이며, 정답 기반 정확도 검증도 없다.

핵심 판단: 현재는 자동 학습 엔진이 아니라 정적 룰 엔진 + 조건부 과거 코멘트 검색이다. DB가 늘어도 status/signature는 자동으로 좋아지지 않는다. 안전장치 없이 코멘트만 늘면 검색 지연·문장 충돌·자기 선례 누출 때문에 오히려 품질이 나빠질 수 있다.
기본 DB 경로 분리 AI 기능 비활성 자동 학습 미구현 선례검색 조건부 가능 통합 기능 테스트 통과

3. 현행 구조: 평가 경로와 기록 경로

잘 되어 있는 부분

  • report_server → eval_analyzer 단방향 의존
  • AI 실패가 web_report 전체를 중단하지 않음
  • 코멘트 재적재 멱등성과 삭제 reconciliation
  • AI Comment 읽기전용 보장
  • raw 편집 시 AI report cache 자동 재평가

연결이 끊긴 부분

  • 평가 읽기 DB와 export 쓰기 DB 기본경로 불일치
  • 온라인 평가 feature/evaluation 미저장
  • 과거 코멘트 자동 백필 없음
  • 사람 정답 status/root cause/outcome 미수집
  • raw 편집 후 export metrics 재계산 없음

4. DB가 쌓이면 무엇이 좋아지고, 무엇은 그대로인가

DB read/write 기본경로 불일치

코멘트는 서랍 B에 쌓이지만 엔진은 서랍 A를 읽는다. 부팅 시 두 절대경로를 비교하고 다르면 AI 기능을 차단해야 한다.

자기 선례·미래 선례 누출

preview와 export의 case ID grain이 달라 현재 세션 코멘트를 선례로 다시 읽을 수 있다. session_id, analysis_key, as_of를 검색 계약에 추가해야 한다.

선례 top-k와 품질 필터 부재

현재는 매칭된 모든 human_comment를 이어 붙인다. DB가 커질수록 느려지고 모순된 조치가 섞일 수 있다.

데몬 스레드 export와 백업 부재

프로세스 종료 시 작업이 유실될 수 있고 eval DB는 report DB 백업 주기에 포함되지 않는다.

카테고리 매핑 왜곡

`issue_category`를 사용하지 않고 worst case를 CPK/ETC에 모두 복제해 의미가 다른 행에 코멘트가 붙을 수 있다.

calibration 선택 편향

저장 게이팅을 통과한 이상 사례 위주의 features 분위수를 정상 경고선으로 사용하면 민감도가 낮아질 수 있다.

AI Comment 활성화 게이트

  1. read/write DB path가 동일하다.
  2. eval DB backup과 restore-check가 성공한다.
  3. legacy 백필 완료율과 실패 목록을 확인할 수 있다.
  4. 현재 세션·미래 사례·동일 analysis_key 누출 테스트가 통과한다.
  5. top-k와 코멘트/prompt 길이 상한이 있다.
  6. AI Comment bridge 회귀 테스트가 있다.
  7. holdout baseline이 기록되어 있다.
  8. 빈 결과와 평가 오류를 구별한다.
  9. 일부 canary 세션만 켤 수 있다.
  10. 즉시 비활성화 kill switch가 있다.

제한: 실제 Windows 서비스 프로세스의 환경변수는 확인하지 못했다. DB 경로 문제는 코드 기본값·현재 셸·기본 `start.bat` 기준이다. 운영 서비스가 별도 `EVAL_DB_PATH`를 주입했다면 실제 연결 상태는 달라질 수 있다.

실제 AI 기능은 현재 비활성이고 eval DB도 없어 실운영 정확도를 측정하지 않았다. 이 문서의 endpoint·테이블·코드 변경은 모두 권고이며 구현하지 않았다.
