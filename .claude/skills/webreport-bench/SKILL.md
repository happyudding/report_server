# web_report 벤치테스트 실행 절차

`tests/bench_webreport.py` 는 임시 DB/디렉토리에 격리된 인프로세스 벤치다 — 운영 서버·DB
무접촉이므로 실행 확인을 따로 받을 필요 없다.

## 1. 실행

기본은 full 스케일(21 소스 × 1000 항목 × 1000 행, 수 분 소요) — **background 로 실행**:

```
server\.venv\Scripts\python.exe tests\bench_webreport.py
```

- 사용자가 "빠르게/간단히" 를 원하면 `--quick` (5×200×200, 수십 초).
- 특정 커밋과 비교하려면 해당 커밋에서 한 번 실행해 기준선을 만든 뒤 현재 코드에서
  재실행하거나, `--baseline tests/bench_results/bench_<ts>.json` 으로 기준을 명시.
- 코드 변경 전후 비교가 목적이면: 변경 **전** 1회 + 변경 **후** 1회 실행 (같은 스케일).

## 2. 결과 해석·요약

완료 후 `tests/bench_results/latest.md` 를 읽고 사용자에게 한국어로 요약한다:

- **`[회귀]`(+30% 초과) / `[주의]`(+15% 초과) 항목을 최우선으로** — 없으면 "회귀 없음" 한 줄.
- 비교 대상이 없으면(첫 실행) 기준선이 만들어졌다고 알린다.
- 핵심 지표만 짚는다: 완전 콜드 열기 / 재오픈(RAM) / 배치 30건 pack vs 폴백 /
  /full 페이로드 크기. 나머지는 리포트 파일 경로 안내로 갈음.
- 회귀가 있으면 "콜드 빌드 단계별" 섹션에서 어느 단계(decode/yield_cpk/tab:* 등)가
  느려졌는지 짚어준다.
- quick 결과는 full 과 비교되지 않는다 (params 일치하는 실행끼리만 비교됨).

## 3. 주의

- 측정 범위 밖: 실 네트워크/waitress 동시성(→ `tests/load_test_10users.py`), 브라우저 JS
  렌더, S3, workers>0. 리포트 말미에 명시돼 있으니 사용자가 물으면 그대로 안내.
- 수치는 PC 사양 종속 — 다른 PC 의 기준선과 절대값 비교는 무의미하다.
- 벤치 스크립트의 측정 대상(라우트·시나리오)을 바꿨다면 기준선 호환이 깨질 수 있음을
  사용자에게 알릴 것.
