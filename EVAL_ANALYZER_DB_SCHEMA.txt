================================================================================
반도체 Fail-Item 평가 분석 엔진 — DB 스키마 설계 (확정본)
================================================================================
목적: 엔지니어의 불량 판단(룰 + 선례 + 코멘트)을 코드로 옮기는 분석 엔진의 저장 구조.
원칙: ① raw(per-DUT 원시값) 저장 안 함 — 계산 시점 메모리 사용 후 요약만 persist
      ② 모든 row 의 grain(= row 1개의 의미)을 명확히 고정
      ③ 파이프라인 전 구간 버전 추적(run_id / engine_version / model_version)
      ④ 룰은 item_name 이 아니라 item_class 로 스코프(일반화·할루시네이션 방지)


================================================================================
0. 개념 — 엔지니어 판단 5단계 ↔ 테이블 매핑
================================================================================
  1 INDEX        무엇을 보는가      → 마스터 + fail_case
  2 RAW MEASURE  무엇을 가져오는가  → raw_metrics
  3 JUDGMENT     어떻게 calc 하는가 → features  (룰이 임계하는 대상)
  4 VERDICT      무엇을 도출하는가  → evaluation + case_signature
  5 HUMAN        사람이 어떻게 판단 → label + case_outcome (정답·결과)

  [3↔4 변환기] thresholds.json + signatures.yaml + bin_taxonomy (데이터 아님; engine_version 에 스냅샷)
  선례(precedent): (signature, item_class, family_product) 로 과거 결과 회수 → 코멘트 근거


================================================================================
1. GRAIN — 각 테이블 row 1개의 의미 (먼저 고정)
================================================================================
  product_master   1 row = 제품 1개(EDS 13자리)
  item_master      1 row = item 정의 1개
  item_alias       1 row = (지저분한 원본 이름 1개 → item_id 매핑)
  item_spec        1 row = (item, product, revision) 의 spec(limit) 1건
  bin_taxonomy     1 row = (product_type, bin) 의 의미 1건
  ingest_run       1 row = 업로드/실행 1건
  run_case         1 row = (run, case) 가 만났다는 사실 1건  (재업로드 이력)
  fail_case        1 row = fail 발생 instance 1건 (product·lot·wafer·item·bin·revision)
  raw_metrics      1 row = (case, run) 의 표준 측정요약 1건
  features         1 row = (case, run, engine_version) 의 판단지표 1세트
  evaluation       1 row = (case, run, engine_version, model_version) 의 기계 판정 1건
  case_signature   1 row = (eval, signature) 1건
  label            1 row = 사람이 단 라벨 이벤트 1건 (case당 다중 가능)
  case_outcome     1 row = case 의 실제 조치·결과 1건 (retest→정상 등)


================================================================================
2. 마스터 / 기준정보
================================================================================
product_master    -- 1 row = 제품 1개
  product_name        PK (EDS 13자리)
  family_product      SOC PMIC / Memory PMIC ...   (cross-product 이력 비교 키)
  product_type        MDDI / PMIC / TCON ...        (spec·임계 분기)
  process             공정정보 (BCD1370F ...)
  inch                8 / 12
  gross_die
  fab_line
  tester              (제품 고정 속성)
  para                (제품 고정 속성)

item_master       -- 1 row = item 정의 1개
  item_id             PK
  item_name_raw       원본 이름
  item_canonical      정규화 이름 (조인·이력 traceability)
  item_base           phase 뗀 본체 (family 키, 예 vref)
  item_phase          단계 접미사 (init/code/trim/p2)
  category_major      TRIM / non-TRIM          ← item_class 구성요소
  category_mid        중분류
  value_type          V / A / Hz / CODE / TCODE / P_F   ← item_class 구성요소
  unit

item_alias        -- 1 row = 원본이름 → item_id
  raw_name            PK
  item_id             FK → item_master

item_spec         -- 1 row = (item, product, revision) 의 limit
  (item_id, product_name, revision)  UNIQUE
  lsl, usl
  updated_at
  ※ spec_margin / SPEC_TOO_TIGHT 의 기준. revision 별 spec 변경 이력 보존.

bin_taxonomy      -- 1 row = (product_type, bin) 의 의미
  (product_type, bin_number)  UNIQUE
  bin_class           defective / abnormal / parametric ...
  severity_bias       status 보정 가중
  description


================================================================================
3. 코어 — case 중심 파이프라인
================================================================================
ingest_run        -- 1 row = 업로드 1건
  run_id              PK
  product_name        FK
  lot_id
  wafer_number
  source_file
  analysis_key        (report.db 역참조)
  ingested_by
  created_at

run_case          -- 1 row = (run, case) 접점  (재업로드 다대다 이력)
  run_id              FK → ingest_run
  case_id             FK → fail_case
  seen_at

fail_case         -- 1 row = fail 발생 instance  (중심 테이블)
  case_id             PK = sha256(product_name | lot_id | wafer_number | item_id | bin | revision)
  product_name        FK
  lot_id
  wafer_number
  item_id             FK → item_master
  bin
  revision
  item_class          = category_major | value_type | bin   ← ★룰 인덱스(denormalized)
  created_at, updated_at
  UNIQUE(product_name, lot_id, wafer_number, item_id, bin, revision)   ← 재업로드 idempotent

raw_metrics       -- 1 row = (case, run) 표준 측정요약  [2 RAW MEASURE]
  PK(case_id, run_id)
  cpk, cpl, cpu
  mean, stdev, min, max
  yield, fail_count, total_count
  bimodality

features          -- 1 row = (case, run, engine_version) 판단지표  [3 JUDGMENT]  (WIDE)
  PK(case_id, run_id, engine_version)
  computed_at
  -- 분포형
  spread_norm, skewness, kurtosis, outlier_ratio, modality,
  bimodality_score, density_gap, cdf_gap
  -- spec margin
  spec_margin_low, spec_margin_high, nearest_spec_side, limit_hit_ratio
  -- 공간
  edge_fail_ratio, center_fail_ratio, radial_gradient, quadrant_imbalance,
  x_gradient, y_gradient, wafer_zone_signature
  -- 기타
  n_dut, site_cpk_delta, code_edge_hit

evaluation        -- 1 row = (case, run, engine, model) 기계 판정  [4 VERDICT]
  eval_id             PK
  case_id, run_id, engine_version, model_version
  status              CRITICAL / MAJOR / MINOR / MONITOR
  confidence
  data_completeness
  evidence_json
  comment             (엔진 생성 코멘트 — 재생성 가능 캐시)
  created_at
  UNIQUE(case_id, run_id, engine_version, model_version)

case_signature    -- 1 row = (eval, signature)
  eval_id             FK → evaluation
  signature
  role                primary / secondary
  score

label             -- 1 row = 라벨 이벤트  [5 HUMAN]  (case당 다중)
  label_id            PK
  case_id             FK
  eval_id             FK (어떤 판정을 보고 달았나)
  human_status
  root_cause_category
  root_cause_detail
  engine_comment_accepted   (bool)
  comment_modified          (bool)
  human_comment       (RAG 본체)
  labeler, reviewer
  label_quality
  created_at

case_outcome      -- 1 row = 실제 조치·결과  [5 HUMAN / 이력]
  outcome_id          PK
  case_id             FK
  label_id            FK (선택)
  action              retest / condition_change / spec_release / dev_feedback / trim_adjust / scrap / monitor
  condition           예 "UVLO_TEST_EN=H"   (조건으로 풀린 지식)
  result              recovered_normal / confirmed_defective / improved / pending
  resolved_by
  resolved_at
  note

engine_version_registry   -- 1 row = engine_version 1개 (버전의 실제 내용)
  engine_version      PK
  thresholds_snapshot
  signatures_snapshot
  taxonomy_snapshot
  created_at


================================================================================
4. 룰 스코프 / 선례 검색 (3↔4 변환 + 코멘트 근거)
================================================================================
룰 인덱스(item_class):
  thresholds.json / signatures.yaml / calibration 은 item_name 이 아니라
  item_class = (category_major[TRIM/non] + value_type + bin) 로 스코프.
  → 룰 일반화·할루시네이션 방지. item_canonical/base 는 traceability·보조 이력용.

선례 검색(precedent):  ※저장 방식(view vs materialize)은 추후 결정
  v_precedent (논리 구조) = fail_case ⋈ item_master ⋈ evaluation/case_signature
                            ⋈ label ⋈ case_outcome 조인
  노출: signature, item_class, family_product, product_type, bin_class,
        root_cause, action, condition, result, comment
  검색 키: (signature, item_class, family_product)
  → 신규 case 에 대해 "retest→정상" "UVLO_TEST_EN H→정상" "spec release" "모과제 동일유형" 회수.


================================================================================
5. 관계 / 버전 체인
================================================================================
  product_master ─┐
  item_master ────┤(FK)
  bin_taxonomy ───┘
        ingest_run ──< run_case >── fail_case ──┬─ raw_metrics      (×run)
                                                ├─ features         (×run×engine)
                                                ├─ evaluation       (×run×engine×model) ─ case_signature
                                                │        └─ label ─ case_outcome
                                                └─ (v_precedent: 위 조인 view)
  체인:  ingest_run → raw_metrics(case,run) → features(case,run,engine)
         → evaluation(case,run,engine,model) → label(eval_id) / case_outcome(case)
  전 구간 버전 추적·재현·비교 가능.


================================================================================
6. 보류(미반영) — 필요해지면 확장
================================================================================
  - per-source 분해 테이블 (raw_metrics_source) : site_cpk_delta drill-down / SOURCE_IMBALANCE 상세
  - dist_digest (quantile/histogram sketch)      : raw 폐기해도 feature 재계산(재현)
  - family_metrics (family_corr, phase_recovery) : 같은 base 의 phase 간 상관 (family grain)
  - RAG embedding (comment_embedding)            : 텍스트 임베딩 검색 (현재는 구조화 precedent 로 시작)
  - CONDITION 측정축 (test_condition)            : 측정 조건(UVLO_TEST_EN, corner)별 fail 추적
  - feature: clamp_ratio(값쏠림), trim_code_margin(TRIM headroom) + signature BIDIR_TAIL
  - precedent materialize (성능 필요 시)


================================================================================
7. 목표 코멘트 ↔ 산출 경로 (검증용 예시)
================================================================================
  ① 양방향 tail → retest 권장 (family서 retest 정상 이력)
       features.tail_ratio_hi/lo (룰) + case_outcome(action=retest, result=recovered_normal)
       + precedent(family_product)              [BIDIR_TAIL 룰은 보류 feature 아님—데이터 있음]
  ② outlier 5%↑ + clamp → UVLO_TEST_EN H 로 정상
       features.outlier_ratio (룰) + [clamp_ratio 보류] + case_outcome(condition="UVLO_TEST_EN=H")
  ③ cpk부족 + TRIM → code margin 부족 → 개발피드백
       raw_metrics.cpk + item_class(TRIM) + [trim_code_margin 보류] + label/outcome(dev_feedback)
  ④ trim후 outlier → 과거 spec tight→release 이력
       features.outlier_ratio + item_phase(trim) + precedent(action=spec_release)
  ⑤ INIT outlier → defective → retest 진성확인
       features.outlier_ratio + item_phase(init) + bin_taxonomy(defective) → 룰
  ⑥ edge성 저수율 → 모과제(sibling) 동일유형 확인
       features.edge_fail_ratio + yield + precedent(family_product cross-product)

  → A(이력/결과)·D(item_class) 반영으로 ①④⑤⑥ 및 ②의 조건지식 생성 가능.
    ②clamp · ③trim_margin · CONDITION 축은 보류분(추후).
