PGM Debug Assistant Architecture

ADVANTEST T2000 기반 Test PGM 개발·디버깅 업무를 AI Agent로 확장하기 위한 1인 개발 로드맵. 일반 프로그래밍 문법 자체가 아니라, T2000 고유 API/Syntax와 반도체 평가 Domain Knowledge를 실행 가능한 형태로 구조화하는 것이 프로젝트의 본질이다.
핵심 자산은 LLM이 아니라 “Domain 및 경험의 코드화”이다. 기존 엔지니어가 머릿속으로 판단하던 Test Sequence, 측정 목적, Resource 선택, T2000 API 사용법, Debug Rule, 실패 패턴, 과거 해결 경험을 Rule / Skill / API Catalog / Golden Code / Debug History로 구조화해야 한다. 이 Knowledge Layer가 안정적이면 Claude·Codex 등 모델이 바뀌어도 시스템의 핵심 경쟁력은 유지된다.

1. Project Overview

Phase 1 · Debug Assistant

사용자의 자연어 요청을 반도체 Domain Intent로 해석하고, 사내 Rule 및 T2000 API/기존 PGM/디버깅 이력을 참고해 실제 T2000 Code를 생성·수정·추천하고 Git Diff까지 보여주는 Assistant.

Phase 2 · Auto Debug Agent

사무실의 사용자 UI → 중앙 Orchestrator → OSAT Client → 실제 T2000 설비를 연결해, 코드 수정·빌드·실행·결과 수집·분석·재수정까지 단계적으로 자동화하는 Agent.

Debug Assistant: 9개월 / Auto Debug Agent: 추가 15개월 → 전체 약 24개월 로드맵.

2. Core Knowledge Architecture

가장 중요한 부분은 “문서를 많이 넣는 것”이 아니라, 엔지니어의 판단 과정을 AI가 호출할 수 있는 구조로 바꾸는 것이다.

① Domain Rule LDO, PLL, ADC, DAC, Leakage, IDDQ, Line/Load Regulation 등 측정 목적과 판단 규칙.
② T2000 API Catalog Class, Method, Parameter, Resource, 제약조건, 사용 예제, Project별 Convention.
③ Skill Layer 예: LDO_LOAD_SWEEP, PLL_LOCK_CHECK처럼 Intent → Required Context → Procedure → API로 연결.
④ Golden Code 실제 현업에서 검증된 Test Class, PGM Pattern, Resource 제어, Logging 및 Error Handling 코드.
⑤ Debug History 증상 → 가설 → Action → Result → Root Cause → Fix 형태로 과거 엔지니어 경험을 구조화.
사용자 요청 "LDO Item load sweep 코드 짜줘" → Intent 분류: LDO_LOAD_SWEEP → Product / Pin / Resource Context 확인 → Domain Rule 조회 → Skill 호출 → T2000 API Catalog 조회 → 유사 Golden Code 검색 → Project 현재 Source 분석 → Code 생성 → Git Diff 생성 → 사용자 승인 / 수정

4. Debug Assistant 동작 예시

예시 입력: “LDO Item load sweep 하는 코드 짜줘. 현재 PGM 기준으로 넣어줘.”
Debug Assistant는 자연어 요청을 바로 코드로 바꾸는 것이 아니라, 현재 PGM 구조와 Domain 지식, 과거 경험을 순서대로 엮어서 T2000 코드 변경안으로 변환한다.

입력 예시 → LDO Item load sweep 하는 코드 짜줘. 현재 PGM 기준으로 넣어줘.
STEP 1
의도 해석
요청을 LDO_LOAD_SWEEP Intent로 해석하고, 단순 Sweep인지 Regulation 확인용인지 등 실제 측정 목적을 분류한다.
STEP 2
현재 PGM + Domain Context 수집
현재 Test Class, Pin/Resource, Power Sequence, Logging 방식, Product 조건을 읽고 필요한 Domain Rule과 함께 현재 상황을 구성한다.
STEP 3
경험 기반 설계
Golden Code, 과거 Debug History, T2000 API Catalog, 사내 Rule/Skill을 참고해 적절한 Test Sequence와 API 조합을 결정한다.
STEP 4
T2000 코드 생성 + Diff
현재 PGM Coding Convention에 맞춰 코드를 생성하고, 원본 대비 변경 Line과 변경 이유를 Git Diff 형태로 보여준다.
STEP 5
Engineer Review + Build Feedback
Engineer가 Apply / Modify / Reject하고, 실제 Build Error가 발생하면 Log를 다시 분석해 수정안을 반복 제안한다.
핵심 포인트: 이 흐름의 본질은 코드 생성 자체가 아니라, 엔지니어가 머릿속으로 하던 판단 순서를 Rule / Skill / Debug History 형태로 코드화하고 그것을 현재 PGM과 연결하는 것이다.

5. Debug Assistant · 9개월 To-do

기간 단계 주요 To-do 완료 기준
1개월차 Domain Mapping 대표 Test 업무 20~30개 정의, LDO/PLL/ADC/DAC/Leakage 등 업무 분류, 엔지니어 판단 Sequence와 Required Context 정리. 자주 사용하는 업무가 Intent/Rule 단위로 목록화됨.
2개월차 Knowledge Schema Domain Rule, T2000 API Catalog, Skill, Golden Code, Debug History DB Schema 설계. 문서형 지식과 구조형 지식 분리. Knowledge 저장 포맷과 CRUD/Search 구조 확정.
3개월차 T2000 API / Source Search Class/Method/API 검색, 기존 PGM 검색, Test Class 검색, Project Context 읽기, Tool 함수 설계. Claude가 Tool 호출로 관련 API와 기존 코드를 찾을 수 있음.
4개월차 Skill Engine LDO_LOAD_SWEEP 등 핵심 Skill 10~20개 작성. Intent → Context → Procedure → T2000 API 흐름 구현. 자연어 요청이 Skill로 안정적으로 매핑됨.
5개월차 Code Generation MVP 현재 Source 분석, T2000 형식 Code 생성, 기존 함수 수정, 프로젝트 Coding Convention 반영. 대표 Test 업무에서 사람이 참고 가능한 코드 생성.
6개월차 Git / Diff Workflow 변경 파일 추적, Git Diff 표시, Apply/Reject, Commit message 생성, 변경 이유 설명. “대화 → 코드 수정 → Diff 확인” Workflow 완성.
7개월차 Build Feedback 사내에서 실제 가능한 Build/Compile 환경 연동, Compiler Error 분석 및 자동 수정 Loop 구현. 주요 Syntax/API 오류를 Agent가 반복 수정 가능.
8개월차 Debug Intelligence 측정 이상 증상 입력 → 유사 Debug History 검색 → 원인 후보 → 확인 Action → 코드 변경안 추천. 단순 코드 생성이 아니라 실제 Debug 조언 가능.
9개월차 Pilot / Evaluation 30~50개 실제 Scenario Evaluation. Intent 정확도, API 선택, Build 성공률, Engineer 수정량, 잘못된 HW Operation 제안율 측정. 현업 Pilot 가능한 Debug Assistant v1.

7. Auto Debug Agent 동작 예시

예시 입력: “이 LDO Item이 100mA 이상에서 Vout Drop이 커져. 원인 찾아줘.”
Auto Debug Agent는 Debug Assistant의 판단 능력 위에 실제 OSAT/T2000 실행 루프를 얹어서 가설 수립부터 결과 해석까지 반복 수행한다.

입력 예시 → 이 LDO Item이 100mA 이상에서 Vout Drop이 커져. 원인 찾아줘.
STEP 1
문제 상황 분석
현재 Fail Item, PGM Revision, Site/Condition, 최근 Result와 유사 Debug History를 모아 증상을 구조화한다.
STEP 2
가설 + Debug Plan 생성
Current Limit, Settling, Contact, Resource Range 등 원인 후보를 우선순위화하고 이를 구분할 최소 Debug Step을 설계한다.
STEP 3
Code Patch + Safety Check
필요한 Debug Patch와 Diff를 만들고, Policy / State Machine으로 승인 필요 여부와 실행 가능 범위를 확인한다.
STEP 4
OSAT Client → T2000 실행
검증된 Typed Command로 checkout → patch → build → load → run → result collect를 수행하고 실행 상태와 Log를 회수한다.
STEP 5
결과 해석 + 다음 Loop
측정 결과를 가설과 비교해 원인을 좁히고, 필요하면 다음 Patch를 생성한다. 해결되면 Root Cause와 Fix를 Debug History에 축적한다.
핵심 포인트: Auto Debug Agent는 AI가 설비를 마음대로 제어하는 구조가 아니라, 가설·판단은 AI가 하고 실제 설비 제어는 Typed Command + Policy + State Machine으로 제한하는 구조여야 한다.

8. Auto Debug Agent · 15개월 To-do

기간 단계 주요 To-do 완료 기준
1개월차 Protocol Design Office ↔ Server ↔ OSAT Client 통신 규격, Request/Response Schema, Command ID, Run ID, Error Code 정의. 통신 규격 문서 및 Mock API 확정.
2개월차 OSAT Client Skeleton Heartbeat, 인증, Command Queue, Result Upload, Logging, 재접속 처리. Tester 없이 Mock Command 수행 가능.
3개월차 Git / Source Control Revision checkout, patch apply, working copy isolation, conflict 처리, rollback snapshot. 원격 코드 변경과 복구가 안정적으로 가능.
4개월차 T2000 Adapter 1 실제 환경에서 가능한 Build/Compile Interface 연결, 상태/로그 수집. OSAT Client가 Build 결과를 서버로 전달.
5개월차 T2000 Adapter 2 Program Load, 특정 Item 실행, Stop, Result/Log 수집 Interface 구현. 제한된 Item에 대해 Remote Run 가능.
6개월차 Orchestrator State Machine IDLE → PATCHED → BUILT → LOADED → RUNNING → RESULT → ANALYZING 상태 정의 및 Timeout/Failure 전이 구현. Tester 상태가 LLM 판단과 분리되어 관리됨.
7개월차 Remote Debug MVP Office UI에서 코드 변경 → Build → Load → Run → Result 확인 End-to-End 구현. AI 자동 판단 없이 원격 Debug Pipeline 완성.
8개월차 Result Normalization Test Result, Log, Fail 정보, Site, Measurement를 Agent가 해석할 공통 Schema로 변환. 제품/PGM별 결과 차이를 공통 포맷으로 취급 가능.
9개월차 Closed Loop 1 Fail → Agent 분석 → 변경안 → 사용자 승인 → Patch → Build → Run → Result 분석. Human-in-the-loop 자동 Debug Loop 1회 이상 안정 수행.
10개월차 Hypothesis Engine 증상 기반 원인 후보 순위화, 과거 Debug History 검색, 다음 확인 Action 추천. Agent가 Debug 순서를 스스로 계획.
11개월차 Safety Policy Voltage/Current/Relay/Power Sequence 등 위험 변경 별 Approval 등급, Limit Rule, Forbidden Action 정의. 위험도 기반 실행 통제.
12개월차 Semi Auto Debug Logging, repeat, settling time 등 저위험 변경은 자동 실행. 고위험 변경은 승인 요구. 저위험 Debug Loop 자동화.
13개월차 Recovery / Reliability Network timeout, Client restart, 중복 명령, Build fail, Tester hang, Rollback, Resume 처리. 장시간 운영에서 상태 꼬임 최소화.
14개월차 Auto Debug Pilot PMIC/LDO 등 좁은 범위에서 목표 기반 자동 가설 → 수정 → 실행 → 분석 Loop Pilot. 대표 Scenario에서 Root Cause 탐색 자동화.
15개월차 Production Hardening Audit Log, Role/Permission, Dashboard, KPI, Action Trace, Fail-safe, 운영 매뉴얼, Versioning. 사내 Pilot/배포 가능한 Auto Debug Agent v1.

9. Final Design Principles

1. Domain First

AI 모델보다 Domain Rule, Skill, Golden Code, Debug History가 먼저다.

2. Thin Office Client

사무실 PC는 UI 중심. 판단과 Knowledge 접근은 중앙 Orchestrator가 담당한다.

3. Dumb OSAT Client

OSAT Client는 판단하지 않고 허용된 명령만 정확하게 실행하고 결과를 반환한다.

4. Typed Command

LLM이 Shell처럼 자유롭게 명령하지 않고 미리 정의된 Tool/API만 사용한다.

5. State Machine

T2000 실제 상태와 Agent 판단을 분리하고 명시적인 실행 상태를 유지한다.

6. Human → Semi → Auto

처음부터 완전자동화하지 않고 승인형 Debug → 저위험 자동화 → 제한적 완전자동화 순으로 확장한다.
