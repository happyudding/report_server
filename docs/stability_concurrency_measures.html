서버 안정화 · 동시접속 대응 보고

리포트 서버가 사용자 증가에도 멈추거나 오류를 내지 않도록 지금까지 적용한 구조 개선과, 이번에 접속 규모가 늘면서 추가로 조치한 내용을 정리했습니다.

2026-08-12 · 목표 규모: 접속 사용자 약 30명, 동시 세션 사용 약 15명 · 서버 자원: 16코어 64GB 중 타 서버 2개 상주 → 이 서버 실효 예산 약 14코어 48GB

요약

  • 결론 — 현재 구조로 “동시 15명이 기존 세션을 조회·편집”하는 주 사용 패턴은 감당 가능합니다. 다만 동시 처리 설정이 과거 10명 기준으로 남아 있었고, 드물지만 서버 전체를 마비시킬 수 있는 경로가 몇 개 확인되어 이번에 조치했습니다.
  • 접근 방식 — 자원 증설이 아니라 중복 계산 제거와 작업 위치 이동으로 해결했습니다. 같은 계산을 사람마다 반복하지 않게 하고, 무거운 계산은 요청 처리 경로 밖으로 빼는 방식입니다.
  • 주요 성과 — 리포트 첫 화면 전송량 55MB → 3.3MB, 웨이퍼 맵 첫 진입 30초 이상 → 3초 이내, 배포 직후 세션 열기 1분 → 5초.
  • 이번 조치 5건 — 동시 처리 스레드 상향, 워커 전멸 연쇄 차단, 저장 시 최대 10초 지연 제거, 오분류된 404 오류 교정, WAL 정리 실패 감지.
  • 남은 사항 — 30명 규모 부하 시험이 미실시이며, 이번 변경은 서버 재기동 후 적용됩니다.

1용어

본문에서 반복되는 용어의 정의입니다.

스레드 (thread) 요청 하나를 처리하는 실행 단위입니다. 서버는 스레드 수만큼 요청을 동시에 받습니다. 대부분 파일·네트워크 대기 상태라 개수를 늘려도 CPU 부담은 크지 않습니다.
프로세스 (process) 독립된 메모리 공간을 가진 실행 단위입니다. 파이썬은 한 프로세스 안에서 CPU 연산이 한 번에 하나씩만 수행되므로(GIL), 무거운 계산을 진짜로 동시에 돌리려면 프로세스를 나눠야 합니다. 스레드만 늘려서는 해결되지 않습니다.
캐시 (cache) 한 번 계산한 결과를 보관해 두었다가 재사용하는 저장소입니다. 이 서버는 메모리·디스크· 완성 응답 3단계로 보관합니다.
콜드 / 웜 (cold / warm) 콜드는 캐시에 없어 처음부터 계산해야 하는 상태(수 초~수십 초), 웜은 이미 계산돼 있어 즉시 응답하는 상태입니다. 성능 문제는 대부분 콜드 경로에서 발생합니다.
HTTP 상태 코드 404 / 503 404는 “해당 자원이 존재하지 않음”, 503은 “일시적으로 처리 불가, 재시도 가능”입니다. 같은 장애라도 404를 주면 사용자는 세션이 삭제된 것으로 판단해 재시도하지 않습니다.
watchdog 서버 상태를 5분 주기로 점검해 응답이 없으면 자동 재기동하는 감시 스크립트입니다. 부하로 응답이 늦은 것을 다운으로 오판하면 정상 서버를 재기동해 사용 중 세션이 끊깁니다.

① 정렬 연산을 클라이언트(Honey)로 이관

문제

Distribution(누적분포) 차트는 측정값을 정렬해야 생성됩니다. 항목 수와 소스 수가 곱해지는 구조라 대용량 세션에서는 정렬만으로 수십 초의 CPU 를 소모했고, 사용자가 열 때마다 같은 정렬을 반복했습니다. 서버에서 가장 무거운 지점이었습니다.

조치

업로드 시점에 Honey 클라이언트가 정렬과 중복 묶기까지 완료한 결과(pack)를 함께 전송하도록 변경했습니다. 서버는 조회 시 누적합(덧셈)만 수행합니다. 정렬은 데이터당 한 번, 업로드하는 PC 에서만 일어납니다.

설계상 유의점

이 결과물은 캐시가 아니라 영구 저장합니다. 캐시로 두면 용량 상한에 걸려 삭제되고 서버 재정렬이 재발하기 때문입니다. 또한 클라이언트 산출값과 서버 계산값이 완전히 동일한지 자동 검사로 확인합니다. 정확도를 희생한 최적화가 아닙니다.

4이번 조치 (2026-08-12)

접속 규모 확대에 따라 점검한 결과 확인된 5건입니다. 증상 기준으로 기술합니다.

조치사유 (미조치 시 발생하는 상황)
요청 스레드 13 → 28
설정 1행		 13은 동시 접속 10명 기준으로 산정된 값입니다. 세션 상세 화면 1개를 여는 브라우저가 여러 요청을 병렬로 보내므로 15명 동시 조회 시 부족해집니다. 이때 서버 상태 점검 요청(/healthz)도 같은 대기열에 들어가 응답하지 못하고, watchdog 이 이를 다운으로 판단해 정상 서버를 재기동합니다. 결과적으로 사용 중이던 세션이 끊깁니다.
워커 전멸 연쇄 차단
큐 대기 60초 상한		 계산 타임아웃(300초)이 큐 대기 시간까지 포함해 측정되었습니다. 대기만 하다 시간을 소진한 작업이 실행 중으로 오인되면 서버가 워커 이상으로 판단해 워커 8개를 전부 강제 종료합니다. 이때 정상 진행 중이던 다른 사용자의 생성 작업까지 동반 실패하고, 실패가 2회 누적되면 해당 세션은 10분간 열 수 없게 됩니다. 이제 아직 시작되지 않은 작업은 60초에 취소하고 워커는 유지합니다.
저장 시 최대 10초 지연 제거 열람 이력·방문자 기록은 실패해도 무시하는 부가 기록인데 DB 경합 시 5초를 대기한 뒤 포기했습니다. 코멘트 저장은 “본 저장(최대 5초) + 부가 기록(최대 5초)”이 직렬로 이어져 합계 10초 지연이 가능했고, 예외를 무시하는 구조라 로그에도 남지 않았습니다. 부가 기록의 대기를 0.15초로 단축했습니다. 사용자 입력을 저장하는 경로는 5초를 유지합니다(유실 방지 우선).
404 오분류 교정
조회·편집 29개 경로 + 세션 상세		 세션과 권한은 정상이고 산출물 파일만 읽지 못한 경우에도 404를 반환했습니다. 404는 “존재하지 않음”을 의미하므로 사용자는 세션이 삭제된 것으로 판단해 재시도하지 않고, 관리자도 신고를 단순 오조회로 처리했습니다. 이제 503과 오류 번호를 반환합니다. 사용자가 번호를 전달하면 관리자가 진단 기록에서 해당 건을 바로 조회할 수 있습니다.
WAL 정리 실패 감지 DB 로그 파일 정리 작업은 읽는 연결이 남아 있으면 예외 없이 실패하는데 반환값을 확인하지 않았습니다. 상시 조회가 있는 서버에서는 매 주기 실패해도 인지하지 못한 채 파일이 계속 증가할 수 있었습니다. 실패 시 경고를 기록하도록 했습니다.
검증 — 신규 자동 검사(오류 코드 교정 5개 항목, 워커 보존 시나리오)를 작성해 통과했고, 기존 자동 검사 12종도 통과했습니다. 성능은 변경 전 코드와 동일 조건에서 나란히 측정해 차이가 없음을 확인했습니다 (Map 3초 SLA 위반 0건). 유의 본 변경은 서버 재기동 후 적용됩니다.
