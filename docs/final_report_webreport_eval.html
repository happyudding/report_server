Web Report & 자동 판정 엔진

테스트 결과 파일을 올리면 리포트가 자동으로 만들어지고, Fail 항목은 엔진이 원인 유형까지 판정해 코멘트 초안을 붙여 준다. 엔지니어가 Excel 로 하던 반복 작업을 시스템으로 옮긴 결과를 정리한다.

2엔지니어 업무에서 달라지는 것

실제 작업 순서대로, 각 단계에서 무엇이 줄었는지 정리한다.

작업 단계기존 방식현재엔지니어 관점 이득
리포트 작성 Excel 에서 수율·CPK 계산, 차트 삽입, 서식 정리 Honey 에서 파일 선택 → 업로드 반복 편집 작업이 사라짐. 분석에 시간을 쓴다
Fail 원인 판단 산포·맵을 하나씩 열어 육안 판단 엔진이 유형을 판정해 현상·조치 문장을 제시, 사람은 검토·수정 놓치는 항목이 줄고, 판단 기준이 통일됨
과거 사례 확인 기억 / 개인 폴더 / 담당자에게 문의 같은 유형의 과거 코멘트가 자동으로 함께 표시 신규·타 제품 담당자도 선배의 판단을 바로 참고
이슈 관리 Excel 파일을 메일로 주고받으며 코멘트 추가 웹에서 PTE / 개발 comment 를 각각 입력, Status 관리 한 화면에서 협의, 버전 엇갈림 없음
이력 조회 과거 Excel 파일을 찾아 연다 제품·Lot·기간으로 검색, 즐겨찾기·중요표시 "예전 그 Lot 은 어땠지" 가 몇 초
조건 비교 표 두 개를 나란히 놓고 눈으로 대조 Before/After 를 시스템이 대조해 바뀐 항목만 표로 변화 지점을 놓치지 않음
데이터 정리 이상치·불필요 항목을 지운 사본을 따로 만든다 원본은 그대로 두고 조회 조건만 조정(되돌리기 가능) 원본 훼손 걱정 없이 여러 관점으로 확인

3자동 판정 엔진 — 무엇을 잡아내나

Fail 항목의 측정값 분포와 웨이퍼상 위치를 함께 보고, 아래 유형 중 어디에 해당하는지 판정한다. 화면에 나오는 문장이 곧 아래 문장이다.

공간 패턴 — 웨이퍼 어디서 Fail 하는가

EDGE_FAIL

E1_FAIL
E1(최외곽) Zone 불량 집중
공정 및 Lot 성 Wafer 성 확인 필요
RING_FAIL
반경 방향으로 Ring 모양 Fail
공정 확인 및 Wafer 성 Lot 성 확인 필요
CENTER_FAIL

UNKNOWN 이 있다는 것이 중요하다. 기존 룰로 설명되지 않는 Fail 을 "판정 못 함" 으로 덮지 않고 명시적으로 표시한다 — 이것이 곧 새 룰을 만들어야 할 후보 목록이 된다.

[현상]
무엇이 관측되었나
판정된 불량 유형을 그대로 문장으로. 시스템이 전량 작성
[사례]
과거엔 어떻게 처리했나

[제안]
무엇을 확인할까
룰이 제시한 조치 방향 + AI 가 사례를 반영해 다듬음
AI 는 보조이지 판정자가 아니다. 불량 유형 판정과 사례 검색은 전부 룰과 데이터가 한다. AI 는 [제안] 문장을 읽기 좋게 다듬는 역할이며, AI 가 동작하지 않아도 룰이 만든 문장이 그대로 표시된다. 판정 결과가 AI 때문에 달라지는 일은 없다.

4이 결과를 믿어도 되는가

자동화 시스템은 "편한가" 보다 "틀리지 않는가" 가 먼저다. 그래서 아래 세 가지를 설계 원칙으로 고정했다.

원칙 1

측정 데이터를 줄이지 않는다

산포 차트는 측정점을 하나도 빼지 않고 그린다. 화면을 빠르게 하려고 점을 솎아내는 방식은 금지돼 있고, 그런 코드는 자동 검사가 저장 자체를 막는다. 속도는 계산 순서를 바꿔서 확보했다.

원칙 2

같은 값은 한 번만 계산한다

Issue Table 의 수율·CPK 는 Yield 탭·CPK 탭의 같은 계산 결과를 가져다 쓴다. 탭마다 따로 계산하지 않으므로 화면끼리 숫자가 다를 수 없다. 한 항목이 탭마다 다른 값으로 보이면 리포트 전체를 못 믿기 때문이다.

원칙 3

사람이 입력한 것은 잃지 않는다

코멘트·Note·차트 주석 등 직접 입력한 내용은 다시 만들 방법이 없다. 그래서 저장 방식 변경은 별도 승인 대상이고, 과거 형식도 계속 읽도록 유지한다. 원본 데이터를 바꾸는 편집과 조회 조건만 바꾸는 편집도 분리돼 있다.

판정 품질을 관리하는 방법

룰은 한 번 만들고 끝나는 것이 아니라 계속 조정해야 하는 대상이다. 그래서 조정 근거를 볼 수 있는 화면을 함께 만들었다.

리더가 갖는 질문답을 주는 화면
이 Fail 은 왜 판정이 안 됐나 항목별로 21개 룰 각각의 실제값과 기준값을 나란히 보여준다. 어느 조건에서 걸렸는지 한 줄로 확인된다
기준값을 바꾸면 어떻게 되나 바꾸기 전후를 같은 데이터로 돌려 판정이 달라진 항목만 비교해 보여준다. 되돌리기도 가능하다
제품마다 기준이 다른데 제품군별로 기준값을 따로 지정할 수 있다. 지정 즉시 반영된다
룰이 실제로 좋아지고 있나 날짜별 정확도·판정 커버리지 추이 그래프. 룰을 고친 시점과 겹쳐 볼 수 있다
전수 검토는 현실적으로 못 한다 룰당 8건만 검수하면 시스템이 기준값 조정안을 제시하고, 승인만 하면 반영된다

5운영 현황

사용 방식

  • Honey(사내 PC 프로그램)로 업로드, 웹 브라우저로 조회
  • PC 계정으로 자동 로그인 — 별도 ID/PW 없음
  • 업로더가 편집 권한을 갖고, 편집자 위임 가능
  • 비공개 세션은 지정된 사람만 조회
  • Honey 는 실행 시 자동 업데이트

데이터 보관

  • 세션 원본과 사용자 입력은 영구 보관
  • 운영 로그만 기간 제한(감사 1년 등)
  • 삭제한 세션은 30일 휴지통
  • DB 자동 백업 주기 운영
  • 원본 Excel 은 서버에 저장하지 않음 — 추출값만 보관

남은 항목

항목상태내용
AI 코멘트 다듬기 기능 현장 확인 개발·테스트 완료. 사내 계정 환경에서의 최종 동작 확인만 남음. 동작하지 않아도 룰 문장은 정상 표시

6의의

1 판단 기준이 조직 자산이 된다

"이 산포는 Contact 문제다" 같은 경험적 판단이 21개 룰과 기준값으로 명문화됐다. 담당자가 바뀌어도 판정 기준이 유지되고, 기준을 바꾸려면 근거를 화면에서 확인하고 바꾸게 되어 변경 이력이 남는다.

2 쓸수록 좋아지는 구조

엔지니어가 남긴 코멘트가 다음 판정의 선례로 되돌아온다. 리포트를 쓰는 행위 자체가 축적이 되고, UNKNOWN 항목은 새 룰의 후보가 된다. 쓰지 않으면 늘지 않고, 쓰면 계속 정교해진다.

3 신규·타 제품 담당자의 진입장벽 완화

경험이 적은 담당자도 불량 유형과 과거 대응을 함께 보게 된다. "무엇을 봐야 하는지 모르는" 상태에서 시작하지 않으므로 숙련도에 따른 리포트 품질 편차가 줄어든다.

4 리포트가 아니라 데이터가 남는다

Excel 파일이 아니라 조회·검색·재분석 가능한 형태로 서버에 쌓인다. 제품·Lot·기간으로 되짚을 수 있고, 앞으로 다른 분석에 재사용할 수 있는 기반이 된다.

이 문서의 판정 문구 21종은 실제 운영 중인 룰 정의에서 그대로 가져온 것이다. 기술 상세는 별도 개발 문서(docs/)에 있다.
