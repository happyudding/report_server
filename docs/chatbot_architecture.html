02 입력에서 출력까지

질문 한 줄이 답으로 바뀌기까지 12단계. 파란 원은 사람이 보는 지점, 회색 원은 서버 내부다. 오른쪽 칩은 그 단계에서 갈라지는 경로다.

  1. 1

    사람이 질문을 입력한다

    chat.js · send()

    { question, conversation_id, context:{ session_id } } 를 POST 한다. CSRF 토큰은 쿠키에서 읽어 X-CSRF-Token 헤더로 되돌려 보낸다. 세션 상세 화면이면 지금 보고 있는 세션 id 가 자동으로 실린다.

    • 60초 초과 → 중단
    • 전송 중 입력 비활성
  2. 2

    관문 — 권한·위조·혼잡

    routes_chat.api_chat()

    master 쿠키가 아니면 404(존재 자체를 숨긴다). CSRF 불일치 403, 빈 질문·500자 초과 400. 그다음 동시 처리 세마포어 3개 중 하나를 10초 안에 잡아야 한다.

    • 비master → 404
    • CSRF → 403
    • 혼잡 → 429
  3. 3

    대화 상태를 꺼낸다

    conversation.recall(conversation_id)

    직전 턴에서 확정된 사실만 돌아온다 — 보여준 세션 목록, 고른 세션, 마지막 항목, 마지막 제품. 질문 원문이나 추론은 저장하지 않는다. 30분이 지났으면 빈 상태다.

    • 만료·미존재 → 빈 상태로 진행
  4. 4

    규칙으로 먼저 분류한다

    planner.rule_plan() — if/elif 13분기

    키워드·정규식으로 인텐트 1개와 슬롯을 뽑는다(제품·항목·기간·서수·이슈필터·상위N·집계축). 근거 없이 catch-all 로 정해졌으면 weak=True 를 단다 — 뒤에서 데이터로 재검증하기 위한 표식이다.

    • 마이크로초 · DB 접근 없음
  5. 5

    약할 때만 LLM 에 물어본다

    planner._needs_llm() → _call_llm()

    unknown·weak·조건 없는 세션검색일 때만 호출한다. 규칙이 확신한 질문은 LLM 을 부르지 않는다 — 슬롯이 3개뿐인데 왕복이 최대 30초라 전부 태우면 네 번째 사용자가 429 를 본다. LLM 은 계획만 세우고 SQL 이나 수치를 만들지 않는다.

    • 현재 미설정 → 이 단계 건너뜀
    • 실패 → 규칙 계획 그대로
  6. 6

    직전 대화를 이어받는다

    agent._run() — 승계 4단계

    ① "1번/첫번째/마지막" → 직전 목록의 N번째 세션 ② 세션 미지정이면 열린 세션 → 직전 세션 ③ 제품 미지정이면 직전 제품 ④ 항목 미지정이면 직전 항목(항목이 주어인 인텐트에서만). 세션 id 는 코드가 목록에서 집는다 — 모델이 문자열을 다시 타이핑하지 않는다.

  7. 7

    인텐트별 핸들러 실행

    agent — handler dict 13개

    핸들러가 필요한 툴을 1~3개 부른다. 모든 호출은 _Trace 에 기록돼 관리자 화면에서 "어느 툴을 어떤 인자로 불렀나"가 남는다.

  8. 8

    조회 — 권한 필터를 통과한 것만

    tools_report / tools_eval / tools_metrics

    report.db 는 비공개 세션 필터를 SQL 에 붙이고, 상세는 _can_view() 로 한 번 더 본다. eval.db 는 파일이 없으면 예외 대신 빈 결과 + db_available:false. web_report 수치는 캐시가 없으면 계산하지 않고 백그라운드 빌드만 예약한다.

    • 콜드 → building + 재시도 버튼
    • eval.db 없음 → 빈 결과
    • 권한 없음 → 없는 것으로 응답
  9. 9

    근거로 재분류 — 모양이 아니라 데이터가 판정한다

    agent._item_history() 말미

    weak 인데 item 축에서 0건이면, 그 토큰을 세션 자유검색에 던져 본다. 세션이 잡히면 인텐트를 session_find 로 고쳐 답한다. "IW06 있어?" 가 항목이 아니라 세션으로 잡히는 이유다.

    • 정상 경로 비용 0 (0건일 때만 프로브)
  10. 10

    답변 문장 + 링크 + 선택 버튼

    _format_* · _link() · _choice()

    문장은 조회 결과를 넣은 템플릿이다(생성 모델이 쓰지 않는다). 링크는 대상이 지금 열린 세션이면 페이지 안 이동(action), 아니면 딥링크 URL 로 갈린다. 애매하면 완성된 후속 질문을 담은 버튼을 준다.

    • 분류 실패 → 광역 폴백(3축 검색)
  11. 11

    사실을 기억하고, 기록을 남긴다

    conversation.remember() · report_db.log_chat()

    대화에는 세션목록·세션·항목·제품만 남긴다. DB 에는 질문·답변 전문·intent·툴 호출·총/대기/LLM 소요 3분해·실패 시 traceback 이 들어간다 — 관리자 Chatbot 탭이 이걸 읽는다.

  12. 12

    화면에 그린다

    chat.js — 렌더

    본문은 textContent 로만 넣는다(HTML 주입 없음). URL 은 /pe/report/ 로 시작할 때만 링크로 만들고, action 은 화이트리스트 3종만 실행한다. 오류면 예외 한 줄 + 접힌 traceback.

    • 대화 id 저장 → 다음 턴에 재사용

05 어떤 개념이 들어갔나

쓴 것과 일부러 안 쓴 것을 함께 적는다. 안 쓴 이유가 곧 이 설계의 근거다.

규칙 기반 분류

채택 · 1차

키워드 세트 20여 개와 정규식 5개로 인텐트와 슬롯을 뽑는다. 13분기 if/elif.

LLM 이 죽어도 서비스가 서 있어야 하므로 이쪽이 하한선이다. 골든셋 64문항이 지키는 것도 이 경로다.

LLM

배선 완료 · OFF

사내 OpenAI 호환 엔드포인트로 POST 1회. 역할은 질문 해석(플래너) 하나뿐 — SQL 을 만들지도, 수치를 쓰지도 않는다.

규칙이 약할 때만 호출한다. 켜면 표현 변형에 크게 강해지고, 꺼도 규칙으로 폴백해 답은 나온다.

엔티티 해석

채택 · 핵심

토큰의 정체를 모양으로 추측하지 않고 DB 에 물어본다. "IW06" 이 제품인지 lot 인지 파일명인지는 10개 컬럼 검색이 답한다.

임베딩 없이 결정론적으로 도는 실질적 리트리버. 오분류를 가장 많이 줄인 장치다.

LangChain / LangGraph

미채택

흐름이 "질문 → 계획 → 툴 1~3개 → 답"으로 끝나 에이전트 루프가 필요 없다.

운영 venv 가 Python 3.14 라 의존 추가 위험이 이득보다 크다. 같은 이름의 실험 패키지가 실제로 운영 장애를 낸 전력도 있다.

RAG · 벡터 검색

보류

검색할 말뭉치 자체가 없다 — eval.db 에 case 1건, evaluation 0건.

구조화 데이터는 SQL 이 더 정확하다. 코멘트·선례가 수백 건 쌓이고 FTS 실패가 측정된 뒤에 올릴 순서다.

멀티턴 메모리

채택 · 구조화

대화록을 다시 보내는 방식이 아니라 사실 4개(세션목록·세션·항목·제품)만 저장한다.

LLM 이 꺼져 있어도 동작해야 하고, 세션 id 같은 식별자는 모델이 다시 타이핑하면 안 되기 때문이다.
